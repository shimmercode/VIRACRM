## ۲. مراحل

```bash
# ۱. کد
git clone <repo> && cd VIRACRM
composer install --no-dev --optimize-autoloader

# ۲. محیط
cp .env.example .env
php artisan key:generate

# ۳. دیتابیس — .env را پر کنید، سپس:
php artisan migrate --force

# ۴. دارایی‌ها
node tools/build-js.mjs
node tools/build-assets.mjs

# ۵. کش تولید
php artisan config:cache
php artisan route:cache
php artisan view:cache

# ۶. دسترسی
chmod -R 775 storage bootstrap/cache
```

**سپس:** کاربر مدیر اولیه با `php artisan vira:create-admin` (پیشنهادی) — چون
reset رمز وب وجود ندارد.

### ۴.۰ ساخت `VIRA_CREDENTIAL_KEY`

```bash
php -r 'echo base64_encode(random_bytes(32)), PHP_EOL;'
```

مقدار را در `.env` (خارج از `public_html`) قرار دهید. این کلید:

- **نباید** با `APP_KEY` یکی باشد
- **نباید** در دیتابیس یا در git باشد
- **باید** جدا از دیتابیس بکاپ گرفته شود (OD-29)

### اگر کلید تنظیم نشده باشد چه می‌شود؟

هیچ خطای ۵۰۰ رخ نمی‌دهد. صفحهٔ دسترسی‌ها باز می‌شود و پیام می‌دهد
«ذخیرهٔ رمز غیرفعال است». ذخیرهٔ رمز **رد می‌شود** — به‌صورت متن ساده نوشته
نمی‌شود. این رفتار عمدی است: سکوت کردن و نوشتن رمز خوانا بدترین حالت ممکن است.

| نشانه | معنا |
|-------|------|
| بنر قرمز «کلید رمزنگاری تنظیم نشده» | `VIRA_CREDENTIAL_KEY` در `.env` خالی است |
| «رمز قابل بازیابی نیست» هنگام مشاهده | کلید عوض شده یا ردیف دست‌کاری شده |
| رمزها بعد از بازیابی بکاپ کار نمی‌کنند | کلید همراه بکاپ بازیابی نشده |

## ۴.۱ مسیر نصب و آدرس دارایی‌ها (Base Path)

این بخش **اجباری** است و در نسخهٔ قبلی این سند نبود. اگر اشتباه تنظیم شود،
هیچ خطایی رخ نمی‌دهد — فقط صفحه بدون استایل می‌آید و شبیه «محیط خراب» به نظر
می‌رسد. همین اتفاق سه بار در محیط Preview افتاد.

### قاعدهٔ واحد

> `ASSET_URL` باید **دقیقاً برابر پیشوندی** باشد که برنامه زیر آن سرویس می‌دهد.

| نحوهٔ نصب | مقدار لازم | آدرس تولیدشده |
|---|---|---|
| دامنهٔ ریشه (`example.com/`) | `ASSET_URL=/` | `/build/css/app.css` |
| زیرمسیر (`example.com/crm/`) | `ASSET_URL=/crm` | `/crm/build/css/app.css` |
| بدون تنظیم (پیش‌فرض) | `ASSET_URL` تعریف نشود | `https://APP_URL/build/...` |

### چرا `/` همیشه درست نیست

مسیرهای ریشه‌ای (root-relative) نسبت به **ریشهٔ دامنه** حل می‌شوند، نه نسبت به
پوشهٔ برنامه. اگر CRM روی `example.com/crm/` نصب شود و `ASSET_URL=/` بماند،
مرورگر `example.com/build/css/app.css` را می‌خواهد — بیرون از برنامه. پاسخ ۴۰۴
می‌آید، CSS لود نمی‌شود، صفحه بدون استایل می‌ماند و **هیچ خطایی در لاگ نیست**.

اندازه‌گیری‌شده در `docs/evidence/review/asset-basepath-matrix.json`:

| سناریو | `ASSET_URL` | نتیجه |
|---|---|---|
| ریشهٔ دامنه | `/` | ✅ استایل اعمال شد |
| زیرمسیر `/crm` | `/` | ❌ بدون استایل (همان اشتباه) |
| زیرمسیر `/crm` | `/crm` | ✅ استایل اعمال شد |

### روش تشخیص سریع

```bash
# در HTML صفحهٔ ورود، آدرس CSS را ببینید:
curl -s https://example.com/crm/login | grep app.css
```

- اگر `href="/crm/build/css/app.css"` است → درست.
- اگر `href="/build/css/app.css"` است ولی سایت روی `/crm` است → `ASSET_URL` را اصلاح کنید.
- اگر `href="https://...` با هاست اشتباه است → `APP_URL` را اصلاح کنید.

### پیش‌فرض روی هاست واقعی

اگر CRM روی دامنهٔ ریشه نصب می‌شود (حالت رایج cPanel با `public_html`)،
**`ASSET_URL` را تعریف نکنید.** در آن حالت آدرس‌ها مطلق و بر اساس `APP_URL`
ساخته می‌شوند که همان دامنهٔ عمومی است و درست کار می‌کند.

`ASSET_URL=/` یک تنظیم مخصوص **محیط Preview** است که پشت پراکسی TLS-terminating
اجرا می‌شود و نمی‌تواند origin خودش را بداند. روی هاست واقعی این مشکل وجود
ندارد، چون `APP_URL` را خودتان صریح تنظیم می‌کنید.

### Vite استفاده نمی‌شود

این پروژه Vite ندارد. دارایی‌ها با `tools/build-assets.mjs` (زنجیرهٔ `@import`
را حل و CSS را الحاق می‌کند) و `tools/build-js.mjs` ساخته می‌شوند و با تابع
`asset()` ارجاع داده می‌شوند. هیچ `manifest.json` و هیچ `@vite` در قالب‌ها نیست.
اگر روزی Vite اضافه شد، `ASSET_URL` همچنان معتبر است ولی این بخش باید بازنویسی شود.

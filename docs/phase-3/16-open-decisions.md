# 16 — تصمیم‌های باز (Open Decisions)

**Vira CRM** · Gate A · ۲ آذر ۱۴۰۵

> **این سند مهم‌ترین خروجی Gate A برای شماست.**
> هر موردی اینجا، جایی است که **من نمی‌توانم بدون اختراع قاعده تصمیم بگیرم**.
> طبق دستور §22.12: «هرگز تصمیم کسب‌وکار تأییدنشده دربارهٔ حقوق یا شرایط قرارداد نگیر».

---

## خلاصهٔ اجرایی: ۳ اقدام از شما

| # | اقدام | چه چیزی را باز می‌کند |
|---|-------|----------------------|
| **۱** | اجرای `host-compatibility-check.php` روی هاست | ۵ میلی‌استون (PDF، scheduler، backup، MySQL) |

## دسته ۱ — بلوکه‌کنندهٔ واقعی (بدون پاسخ، کار متوقف است)

### OD-16 — فرمول حقوق و دستمزد 🔴 **مهم‌ترین**

**وضعیت:** `BLOCKED` · الزام `REQ-07.02` (P0)

**مسئله:** سند مرجع §7 می‌گوید حقوق «قابل تنظیم» باشد و اقلام (پایه، پورسانت
پروژه، پاداش، اضافه‌کاری، کسور، مساعده) را نام می‌برد، ولی **هیچ فرمولی نمی‌دهد**.

**چرا نمی‌توانم حدس بزنم:** فرمول حقوق، تعهد مالی است. اگر اشتباه پیاده شود،
یا کارمند کم می‌گیرد یا شرکت ضرر می‌کند. این دقیقاً همان چیزی است که دستور §22.12
ممنوع کرده.

**گزینه‌ها:**

| گزینه | توضیح | پیامد |
|-------|-------|-------|
| A | **پورسانت = درصدی از مبلغ قرارداد پروژه** | نیازمند درصد در تنظیمات |
| B | **پورسانت = مبلغ ثابت به‌ازای هر پروژه** | ساده‌ترین |
| C | **پورسانت = ضریب × تعداد پروژه** | مثل «۳ پروژه فعال = X» |
| D | ترکیب A/B بر اساس نوع پروژه | پیچیده‌تر |
| E | **هیچ پورسانتی نیست؛ فقط حقوق ثابت + اقلام دستی** | ساده‌ترین و امن‌ترین |

**پیشنهاد من:** گزینهٔ **E** برای نسخهٔ ۱ + جدول `payroll_rules` که بعداً هر
استراتژی را بپذیرد. یعنی حقوق ثابت + اقلام دستی (پاداش/کسور/مساعده) که مدیر
وارد می‌کند. **این هیچ قاعده‌ای اختراع نمی‌کند** و نیاز سند (فیش ماهانه) را برمی‌آورد.

**سؤال دقیق از شما:** آیا پورسانت پروژه‌ای در حقوق لازم است؟ اگر بله، فرمولش چیست؟

### OD-32 — افزودن mPDF به‌عنوان موتور PDF 🔴

**وضعیت:** `BLOCKED` · الزامات `REQ-06.05`, `REQ-07.03`, `REQ-09.05`

**مسئله:** هیچ موتور PDF نصب نیست. چهار سند الزامی است.

**تحلیل:** در `12-pdf-document-architecture.md` شش گزینه بررسی شد. تنها گزینه‌ای
که **هم فارسی/RTL را بومی درست می‌دهد و هم روی هاست اشتراکی بدون باینری/Node نصب
می‌شود** mPDF است.

| اثر | جزئیات |
|-----|--------|
| وابستگی جدید | `mpdf/mpdf` (Composer) |
| نیاز PHP | `mbstring`, `gd` — **باید H-11 تأیید کند** |
| حافظه | ۲۵۶M توصیه‌شده (H-16) |
| جایگزین | DomPDF — **فارسی ضعیف**، توصیه نمی‌شود |

**پیشنهاد:** تأیید افزودن mPDF.

### OD-07 — مرز روز و ساعت اجرای زمان‌بند 🟠

**وضعیت:** `BLOCKED` جزئی · الزام `REQ-12.07/08` (هر دو P0)

**مسئله:** «۲ روز تقویمی قبل» دقیق است، ولی:
- ساعت اجرا؟
- timezone؟
- اگر cron وجود نداشت (H-15)، چه؟

**پیشنهاد:** `Asia/Tehran`، اجرا ۰۸:۰۰، مرز روز = نیمه‌شب تهران.

**سؤال:** آیا ۰۸:۰۰ مناسب است یا ۰۰:۰۱ (تا اول صبح در کارتل باشد)؟

## دسته ۲ — قواعد کسب‌وکار که سند سکوت کرده

### OD-34 — فهرست دقیق Placeholderهای قرارداد 🟠

**الزام `REQ-04.05`**

سند می‌گوید «جایگذاری خودکار اطلاعات مشتری» ولی فهرست نمی‌دهد.

**پیشنهاد (۱۲ placeholder):**

| placeholder | منبع |
|-------------|------|
| `{{customer_name}}` | نام یا نام شرکت |
| `{{customer_type}}` | حقیقی/حقوقی |
| `{{customer_national_id}}` | کد ملی / شناسه ملی |
| `{{customer_address}}` | آدرس کامل |
| `{{customer_phone}}` | موبایل |
| `{{customer_website}}` | دامنهٔ اصلی |
| `{{contract_title}}` | عنوان |
| `{{contract_amount}}` | مبلغ (تومان، فارسی) |
| `{{contract_amount_words}}` | مبلغ به حروف |
| `{{start_date}}` | تاریخ شروع شمسی |
| `{{end_date}}` | تاریخ پایان شمسی |
| `{{service_description}}` | شرح خدمات |

**قاعدهٔ سخت:** placeholder ناشناخته → **خطا**، نه رندر خالی. (وگرنه قرارداد با
«{{custmer_name}}» امضا می‌شود.)

**سؤال:** موردی کم/زیاد است؟

### OD-35 — آستانه‌های هشدار انقضا 🟠

**الزام `REQ-02.04`**

سند مثال ۳۰/۱۵/۷/۳ روز را می‌دهد. الان فقط یک عدد (`contracts.expiry_warning_days = 30`).

**پیشنهاد:** چند آستانه در تنظیمات، پیش‌فرض `[30, 15, 7, 3]`، هر قرارداد در
کارتل با نزدیک‌ترین آستانه برچسب بخورد.

**سؤال:** این چهار عدد درست است؟

### OD-11 — SMTP و ارسال ایمیل 🔵

سند یادآوری را «اعلان» می‌گوید. **اعلان درون‌برنامه‌ای (کارتل) کافی است یا ایمیل هم لازم است؟**
اگر ایمیل: SMTP هاست چیست؟

**پیشنهاد:** نسخهٔ ۱ فقط درون‌برنامه‌ای. ایمیل در فاز بعد.

## دسته ۳ — امنیت و عملیات

### OD-26 — Re-authentication برای Reveal رمز 🟠

آیا برای دیدن رمز وردپرس مشتری، کاربر باید رمز خودش را دوباره وارد کند؟
- **گزینه A:** همیشه re-auth (امن‌ترین، آزارنده‌ترین)
- **گزینه B (پیشنهاد):** اگر نشست > ۱۵ دقیقه، re-auth
- **گزینه C:** فقط Audit، بدون re-auth

### OD-29 — اعلام ریسک از دست رفتن کلید رمزنگاری 🔴

**این را باید کتباً تأیید کنید:**
> اگر `VIRA_CREDENTIAL_KEY` گم شود، **همهٔ رمزهای دسترسی مشتریان بازگشت‌ناپذیر
> می‌شوند**. بکاپ دیتابیس بدون این کلید، رمزها را بازیابی نمی‌کند.

**پیشنهاد:** کلید جدا از `APP_KEY`، در مدیر رمز/گاوصندوق، در بکاپ **نه** (جدا نگهداری).

### OD-31 / OD-33 — رمزگذاری PDF و عمر فایل محرمانه

- PDF محرمانه با رمز باز شود؟ (mPDF پشتیبانی می‌کند)
- فایل چند ساعت بماند؟ (پیشنهاد: ۲۴ ساعت، سپس حذف)

### OD-09 / OD-28 — نگهداری بکاپ و دادهٔ شخصی

- بکاپ چند روز نگه داشته شود؟
- دادهٔ شخصی کارمند پس از خروج چند وقت نگه داشته شود؟ (الزام قانونی ایران؟)

## دسته ۴ — تصمیم‌های محصول/UI

### OD-22 — صفحهٔ مستقل «کارتابل کامل»؟

دلیل: سند §2 داشبورد را مرکز کار روزانه می‌داند؛ صفحهٔ دوم تکرار است.

### OD-23 — «گزارش‌ها» یک صفحه یا چهار؟

دلیل: IA ساده‌تر، وضعیت در URL، Pagination درست.

### OD-24 — «تنظیمات / Audit / بکاپ» یک آیتم یا سه؟

**پیشنهاد: یک آیتم «مدیریت» + tabs داخل صفحه.**

### OD-25 — «دسترسی‌های پروژه» آیتم مستقل سایدبار؟

**پیشنهاد: بله.** نیاز واقعی: «کجا رمز این دامنه بود؟» جستجوی سراسری می‌خواهد.

### OD-27 — نمایش مبلغ: تومان یا ریال؟

دیتابیس `integer` ریال است. نمایش چیست؟
**پیشنهاد: تومان در UI** (خواناتر برای مدیر ایرانی)، ریال در DB فقط.

### OD-36 — آیا سند مرجع اصلی (`docx`) قابل دریافت است؟

`docs/requirements/requirements.catalog.yaml` صریح می‌گوید:
> `document_status: "NOT_AVAILABLE_IN_REPO"`

مواد از **متن استخراج‌شده** (`source/Vira_CRM_Requirements_FA.txt`، ۳۰۴ خط، ۱۵ بخش)
دریافت شده که **معتبر و کافی** است. اگر `.docx` اصلی موجود است، برای تطبیق بند‌به‌بند
ارسال کنید.

## آنچه نیاز به تصمیم شما **ندارد** (فکر کردم و تصمیم گرفتم)

این‌ها را خودم تصمیم گرفتم چون از سند یا کد قابل استنتاج بودند، و صریح ثبت می‌کنم
تا بتوانید رد کنید:

1. مبلغ در DB به ریال `integer` می‌ماند (بدون float).
2. `expiring` وضعیت مشتق می‌ماند، نه قابل انتخاب.
3. Layout سایدبار به ۹ آیتم کاهش می‌یابد (نه ۳۰).
4. «قرارداد فعال» صفحهٔ جدا نمی‌شود، فیلتر `/contracts?status=active` است.
5. Repository Pattern و Event Sourcing اضافه نمی‌شوند.
6. Tailwind اضافه نمی‌شود؛ CSS توکن‌محور می‌ماند.
7. رنگ برند دست‌نخورده می‌ماند.
8. ایموجی به‌جای آیکن استفاده نمی‌شود.

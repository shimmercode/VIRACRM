## 1. Composer dependency lock — BLOCKED

### 1.1 Why Packagist fails, precisely

Three independent causes, each confirmed by execution. Any one of them alone
would be enough.

**(a) Composer cannot spawn a process in this PHP runtime.**

The only PHP available is a WebAssembly build (`php-wasm 8.3.36`). Its
process-spawning functions are compiled out:

```
$ proc_open('git --version', $descriptors, $pipes)
→ SPAWN_UNSUPPORTED, "not a resource"

code: 'SPAWN_UNSUPPORTED'
at php.wasm.zif_shell_exec (...)
```

`function_exists('proc_open')` returns `true`, which is why this was not obvious
at first — but every call fails. Composer shells out to `git` and `unzip` for
dist downloads, so it cannot install anything here even with network access.
`exec()` and `shell_exec()` fail the same way.

**(b) Packagist is unreachable at the TLS layer.**

```
$ python3 -c "urllib.request.urlopen('https://repo.packagist.org/packages.json')"
URLError: <urlopen error TLS/SSL connection has been closed (EOF)>
```

This is not a proxy misconfiguration on our side; the remote host closes the
handshake. Notably `https://api.github.com` returns **200**, so the restriction
is specific to Packagist and the Debian mirror (see gate 2), not general
egress.

**(c) No local cache or mirror exists.**

```
~/.composer            absent
~/.cache/composer      absent
vendor/composer/       absent  ← no installed.json
```

There is therefore **no legitimate source** from which a `composer.lock` could be
derived. Writing one by hand — inventing version numbers and content hashes for
~80 packages — is fabrication, which the directive forbids and which would be
actively dangerous: a lockfile full of wrong hashes produces an install that
fails obscurely, or worse, resolves to different code than what was tested.

### 1.2 What the dependency tree actually is

`vendor/` in this repository is **not** a Composer tree. It is generated by
`tools/resolve-vendor.py`, a GitHub-only resolver that downloads release archives
and writes a PSR-4 autoloader, layout `vendor/<org>--<pkg>/`.

```
$ python3 tools/resolve-vendor.py --verify
OK: vendor/ has 80 packages and an autoloader
exit 0
```

That script's own docstring is honest about what it is:

> This is a DEVELOPMENT-ONLY workaround. On the client host the project is
> installed with real Composer against Packagist. `composer.json`/`composer.lock`
> remain the source of truth for production.

`composer.json` declares `php ^8.2`, `laravel/framework 12.40.0` (pinned),
`mpdf/mpdf ^8.2`, and dev dependencies (phpunit `^11.5.3`, pint, sail, etc.).
The application boots and 69 suites pass against this resolved tree — that is
real, and it is why the *application* can be assessed. It is not evidence that
`composer install` reproduces the same tree.

### 1.3 What was attempted

| Attempt | Result |
|---|---|
| `composer` on PATH | not installed |
| `/tmp/composer.phar` | **not a phar** — gzip-compressed tar of Composer 2.11.2 source |
| extract + `php bin/composer` | "You must set up the project dependencies using `composer install`" |
| Composer source vendored by hand | abandoned — Composer itself needs `proc_open` |
| derive lock from `vendor/` dist refs | impossible — no `installed.json`, layout is not Composer's |
| reach `repo.packagist.org` | TLS EOF |
| reach a mirror | none configured; no cache |

> The `.phar` deserves a note. It began as a 615,266-byte file whose first bytes
> are `\x1f\x8b\x08` — gzip, not PHP. Running it produced a bizarre
> `unexpected character 0x1A` parse error, which read like a runtime fault and
> was actually a mislabelled archive. Checking magic bytes first would have saved
> a detour.

### 1.4 The exact commands to complete this gate

On the client host, or any machine with Packagist access:

```bash
composer validate --no-check-publish
composer install --no-dev --optimize-autoloader
composer check-platform-reqs
php artisan --version          # must print, proving the tree boots
```

Then commit the resulting `composer.lock` and re-run the suite roster.

**Responsible party:** engineering, on networked hardware.
**Risk while blocked:** the production dependency tree is not bit-reproducible.

## 2. MySQL / MariaDB compatibility — BLOCKED, with one proven defect

Full analysis in **`docs/MYSQL_COMPATIBILITY_REPORT.md`**. Summary:

### 2.1 Provisioning failed for three independent reasons

- no `mysqld`/`mariadbd`, no `docker`/`podman`, no installer script;
- `apt-get update` cannot even open its lock (uid 1001);
- `deb.debian.org` closes the TLS connection (`EOF`), so privileges would not help.

`systemctl` exists but has no init system behind it
(`Failed to connect to bus: No such file or directory`).

### 2.2 A real defect was found anyway

`vira:backup` is built on `SQLite3::backup()` and reads
`database.connections.sqlite.database` rather than the default connection.

```
$ DB_CONNECTION=mysql DB_DATABASE=vira_prod php tools/checks/backup-driver-probe.php
backup source : sqlite.database = vira_prod
live source   : mysql.database  = vira_prod
is the backup source a file on this host? NO — it is not a path at all
RESULT: MISMATCH.        exit 1
```

On a MySQL host that value is a schema name, not a path. The command would not
back up the live database. **This blocks the MySQL cutover** independently of the
regression, and is the single most consequential finding of this round.

### 2.3 Static review only — and not counted as evidence

`utf8mb4`/`utf8mb4_unicode_ci`, 191-length indexes, version-gated CHECK
constraints (MySQL 8.0.16+ / MariaDB 10.2.1+), integer Rial instead of floats,
and PHP-side Persian normalisation all look sound. **None of it is a pass.**
SQLite does not enforce foreign keys by default, so 69 green suites say nothing
about whether the 96 declared foreign keys hold on MySQL.

## 3. Security and HTTPS — PASS at the application layer, BLOCKED at transport

Full record in **`docs/SECURITY_DEPLOYMENT_ACCEPTANCE.md`**.
`security-deployment.mjs` **16/16** · `security-headers.mjs` **16/16**.

### 3.1 A defect the tests were hiding

The attempt to test trusted proxies found that **the harness could not test
them**. `tools/http-render.php` set `$_SERVER['REMOTE_ADDR']`, then built the
request with `Request::create()`, whose server-bag argument was `[]`.
`Request::create()` does not read `$_SERVER`; it defaults the peer address to
`127.0.0.1`. So `$request->ip()` was the loopback address on every request, and
any assertion about `last_login_ip`, audit attribution or login throttling would
have passed on the default value regardless of configuration.

This is the same class of bug as a test that passes because it asserts nothing.
It was fixed by setting the server bag — the pattern the file already used for
`HTTPS` — and by adding an opt-in `remote_addr` field, defaulting to the old
behaviour so no existing suite changed.

### 3.2 What the fixed harness then proved

| Case | `last_login_ip` |
|---|---|
| `TRUSTED_PROXIES` unset + forged `X-Forwarded-For` | real peer — **ignored** |
| `TRUSTED_PROXIES=10.0.0.5`, arrival from `10.0.0.5` | forwarded client — **honoured** |
| `TRUSTED_PROXIES=10.0.0.5`, arrival from elsewhere + forged header | real peer — **ignored** |

The third case is the argument against wildcards, demonstrated rather than
asserted.

### 3.3 Also verified

- **Cookies:** `HttpOnly`, `SameSite=Lax`, `Path=/`; `Secure` defaults **true**
  when `APP_ENV=production` and the variable is absent — proven by booting the
  real config with the line stripped.
- **Session:** logout destroys the authenticated row (0 of 1 remain); a session
  aged past 120 minutes is refused (302 → `/login`).
- **Keys:** `vira:backup-key` emits 32-byte base64, differs per run, and the
  output actually produces a readable container. It prints rather than editing
  `.env` — a command that silently rewrites an environment file can put a
  secret in the wrong place.
- **Headers:** `nosniff`, `DENY`, `same-origin`, `no-referrer-policy` set,
  `permissions-policy`, 7-directive CSP with `script-src 'self'` and **no**
  `unsafe-inline`, no `X-Powered-By`.
- **`Cache-Control: must-revalidate, no-cache, no-store, private`** on
  authenticated data pages, verified on `/customers`.
- **No secrets** in Git or in 2.8 MB of logs.

### 3.4 BLOCKED: transport

No TLS terminator exists here. The HTTP→HTTPS redirect, HSTS, TLS version and
cipher policy, and certificate validity are all **unverified**. What is verified
is the application's half: `Secure` cookies in production, and the forwarded
protocol honoured only from a configured proxy.

**Responsible party:** client operations. The nginx configuration is in
`docs/SECURITY_DEPLOYMENT_ACCEPTANCE.md` §7.

## 4. Backup and restore — PASS on SQLite, BLOCKED on scheduling

Full record in **`docs/BACKUP_RESTORE_ACCEPTANCE.md`**.
`backup-hardening.mjs` **16/16**, exit 0.

| Client requirement | Status |
|---|---|
| Backup from a disposable database | **PASS** — exit 0 |
| Verify encryption | **PASS** — 7.990 bits/byte, no SQLite magic, no plaintext Persian |
| Verify integrity | **PASS** — GCM tag; 1-bit flip → exit 1 |
| Destination outside document root | **PASS** — `public/*` refused, incl. `..` and symlink |
| Restore into separate empty database | **PASS** — exit 0 |
| Compare logical fingerprints | **PASS** — **all 56 data tables identical** (485 rows) |
| Verify records and relationships | **PASS** — `foreign_key_check` clean, 0 orphans |
| Failed restore leaves original intact | **PASS** — exit 1, **0 tables changed**, audited |
| Scheduled execution via real cron | **BLOCKED** — no cron, no init system |

### 4.1 The fingerprint test, and why `audit_logs` is excluded

Row counts cannot detect a rewritten column — that is exactly how a content leak
was missed earlier in this project. The comparison is therefore a content digest
per table.

`audit_logs` is excluded deliberately: the backup appends `backup_ok` to the
source after writing the container, and the restore appends `restore_ok` to the
target. That difference *is* the record that both operations happened. Demanding
a whole-database digest match would make a correct restore fail — and would
tempt the next engineer to weaken the check.

### 4.2 The failed-restore test compares data, not bytes

A failed restore appends a `restore_failed` audit row, which is correct
behaviour — a refusal with no trace is indistinguishable from a backup that
never ran. A byte-for-byte file comparison would therefore fail a restore that
did the right thing. The assertion is that **0 data tables changed**, which is
the property that matters: a bad container cannot half-overwrite a good database.

### 4.3 Scheduling is honestly BLOCKED

`crontab`, `cron`, `crond`, `anacron`, `at` are all absent; `systemctl` cannot
reach a bus; `/etc/cron.d` is an empty root-owned directory with no daemon.
Writing a crontab file that nothing executes, and calling it verified, is the
failure mode the directive forbids.

The command *is* schedule-safe — pruning happens only after a successful,
audited container, and two runs produce two distinct files — but the scheduler
is unverified. The cron line and its verification procedure are in
`docs/BACKUP_RESTORE_ACCEPTANCE.md` §8.

### 5.3 Finding: one phantom citation, corrected

`REQ-02.02` claimed evidence from **`work-items-flow` 13/13** — a suite that does
not exist. The real suite is `work-item-flow` (singular) and it does report
13/13, so the *count* was right and only the *name* was wrong. The summary also

A citation that cannot be followed is worse than none: it looks like proof.

### 5.4 The honest reading

**Why this is not wired into the regression roster.** Every suite in
`run-all.mjs` is `required: true` with no per-suite opt-out, so adding this tool
would turn the roster permanently red until all 58 are backfilled. That is a CI
policy decision with real consequences for the client, and making it unilaterally
at the end of a delivery would be the wrong call. The tool is therefore a
standalone audit — exit 1 today — and the gap is recorded here as risk 6 rather
than converted into a build failure. Whoever owns the pipeline should decide
whether to wire it in **after** the backfill, so the check can be green from the
day it is enforced.

The 58 items are not necessarily wrong — most describe things that plainly exist
(customers, contracts, projects) and are covered by suites. But **the directive's
standard is a pointer, not an assertion**, and by that standard 58 of 63 do not
meet it. Backfilling them properly is a documentation task of real size, not
something to fake with a bulk regex, and it is listed as an open item rather than
declared done.

In order. None can be completed in this environment.

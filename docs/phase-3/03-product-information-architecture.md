# 03 — معماری اطلاعات محصول (Information Architecture)

**Vira CRM** · Gate A · ۲ آذر ۱۴۰۵

هدف: مدیر باید در **حداکثر دو گام** به مهم‌ترین کارها برسد، و سایدبار نباید به
درخت تو در تو تبدیل شود.

---

## ۱. اصل حاکم بر ناوبری

دستور §06 یک IA پیشنهادی با ۶ گروه و ۳۰+ آیتم داد. آن را **حذف نکردم، ولی
ساده‌ترش کردم**، چون:

1. **۳۰ آیتم در سایدبار = ناوبری غیرقابل اسکن.** هر آیتم اضافی، سرعت رسیدن به
   آیتم اصلی را کم می‌کند.
2. بیشتر آیتم‌های پیشنهادی **صفحه نیستند، فیلترِ یک صفحه‌اند**: «قراردادهای فعال»
   و «قراردادهای در آستانه انقضا» فیلترِ `/contracts` هستند، نه صفحهٔ جدا.
3. سند مرجع ۱۵ بخشی **چند گروه** را اصلاً نام نمی‌برد (مثل «Analytics» به‌عنوان
   بخش مستقل).

## ۲. سایدبار نهایی (۹ آیتم، دو گروه)

```
┌─ فضای کاری ─────────────────────────┐
│  🏠  داشبورد                          │  ← کارتل: عقب‌افتاده/امروز/پیش‌رو
├─ عملیات ────────────────────────────┤
│  👥  مشتریان                          │
│  📄  قراردادها                        │
│  📁  پروژه‌ها                          │
│  🔑  دسترسی‌های پروژه                  │
├─ سازمان ────────────────────────────┤
│  💼  پرسنل                            │
│  💰  حقوق و دستمزد                    │
├─ تحلیل و مدیریت ────────────────────┤
│  📊  گزارش‌ها                          │
│  ⚙️  تنظیمات                          │
│  🛡️  رویدادها (Audit)                 │
└─────────────────────────────────────┘
   (پایین: کاربر / تغییر رمز / خروج)
```

**۹ آیتم** — در برابر ۳۰+ پیشنهادی. همه با مجوز فیلتر می‌شوند (موجود: `config/navigation.php`).

### چرا «کارتابل/یادآوری» آیتم مستقل نشد

دستور پیشنهاد `Workspace → My Tasks / Reminders / Notes` داد. اما:
- **کارتل در داشبورد است** و سند مرجع §2 صریحاً می‌گوید داشبورد مرکز کار روزانه است.
- یک صفحهٔ «یادآوری» جدا، مدیر را مجبور می‌کند بین دو جا سوئیچ کند.
- **تصمیم:** کارتل در داشبورد می‌ماند + فیلتر «فقط کارهای من» و «همه» در همان صفحه.
  یادداشت‌ها از **پروندهٔ مشتری/پروژه** ایجاد می‌شوند و در کارتل دیده می‌شوند.

این یک **تصمیم نیازمند تأیید** است (OD-22). اگر صفحهٔ مستقل «کارتابل کامل» می‌خواهید،
بگویید — اما آن را تکرار داشبورد نمی‌کنم.

## ۴. الگوی «فیلتر به‌جای صفحهٔ جدید»

این‌ها **صفحهٔ獨立 نمی‌سازند**، فیلتر روی صفحهٔ موجود هستند:

| خواستهٔ ظاهری | پیاده‌سازی واقعی |
|---------------|-----------------|
| قراردادهای فعال | `/contracts?status=active` ✅ |
| قراردادهای در آستانه انقضا | `/contracts?status=expiring` |
| قراردادهای منقضی | `/contracts?status=expired` |
| پروژه‌های سئو | `/projects?type=seo` |
| پروژه‌های طراحی | `/projects?type=design` |
| پروژه‌های یک کارشناس | `/projects?owner={id}` |
| تخصیص‌های پرسنل | `/employees/{id}#assignments` |
| فیش‌های یک کارمند | `/payroll?employee={id}` |
| گزارش‌های مالی | `/reports?type=financial` |
| گزارش‌های قرارداد | `/reports?type=contracts` |
| گزارش‌های پروژه | `/reports?type=projects` |
| گزارش‌های پرسنل | `/reports?type=payroll` |

**مزیت:** ۱۲ «صفحه» حذف می‌شود، وضعیت در URL حفظ می‌شود، چیپ فیلتر کار می‌کند،
و Pagination درست می‌ماند.

## ۵. جریان‌های کاربری کلیدی (۵ گردش‌کار اصلی)

### جریان ۱ — مشتری تا قرارداد (هستهٔ محصول)

```
داشبورد → مشتریان → [ایجاد] → فرم مشتری
                              ↓ (تشخیص تکراری)
                         پروندهٔ مشتری
                              ↓ [+ قرارداد]
                    ایجاد قرارداد → انتخاب نوع
                              ↓
                      انتخاب قالب → جایگذاری خودکار
                              ↓
                    ویرایش متن → پیش‌نمایش PDF
                              ↓
                      [نهایی‌سازی] → snapshot نسخه
                              ↓
                      PDF ذخیره‌شده (تغییرناپذیر)
```

**قاعدهٔ سخت:** پس از نهایی‌سازی، ویرایش قالب **نباید** سند نهایی را تغییر دهد.
این الزام `REQ-04.07` است و باید با تست اثبات شود.

### جریان ۲ — پروژهٔ سئو با دسترسی‌های اجباری

```
پروژه‌ها → [ایجاد پروژهٔ سئو] → پیش‌نویس ذخیره می‌شود
                                    ↓
                          افزودن دسترسی‌ها (WordPress/Hosting/...)
                                    ↓
                        ⚠️ تلاش برای نهایی‌سازی
                                    ↓
                    ┌───────────────┴───────────────┐
                    │ دسترسی اجباری ناقص؟           │
                    │  بله → ❌ مسدود با پیام صریح  │
                    │  خیر → ✅ نهایی               │
                    └───────────────────────────────┘
                                    ↓
                    PDF عمومی (بدون رمز) + PDF محرمانه (با رمز)
```

### جریان ۳ — یادآوری فاکتور و گزارش (مستقل)

```
ایجاد رویداد فاکتور  ──→ یادآور فاکتور (D-2, D-0, عقب‌افتاده)
ایجاد رویداد گزارش   ──→ یادآور گزارش   (D-2, D-0, عقب‌افتاده)
   ↑ دو زنجیرهٔ کاملاً مستقل
تغییر تاریخ → بازمحاسبهٔ همان یادآور (نه ساخت دومی)
انجام فاکتور → یادآور گزارش باز می‌ماند
```

### جریان ۴ — حقوق با حفظ تاریخچه

```
پرسنل → [ایجاد] → حقوق پایه
              ↓
     دورهٔ حقوق → محاسبه → snapshot ورودی‌ها
              ↓
        بازبینی → [تأیید] → فیش PDF
              ↓
     تغییر حقوق فعلی  ──✈──✗──→  فیش گذشته تغییر نمی‌کند
```

### جریان ۵ — دسترسی محرمانه (حساس‌ترین)

```
دسترسی‌های پروژه → فهرست ماسک‌شده (••••••)
                        ↓ [نمایش]
              درخواست سرور + بررسی مجوز credentials.reveal
                        ↓
                   ثبت در AuditLog (بدون مقدار رمز)
                        ↓
              نمایش ۳۰ ثانیه → خودکار مخفی
                        ↓ [خروجی PDF محرمانه]
              مجوز credentials.export + ثبت + فایل با هشدار محرمانگی
```

## ۶. قاعدهٔ مجوز در ناوبری (سه‌لایه)

| لایه | چه می‌کند | آیا امنیت است؟ |
|------|-----------|----------------|
| سایدبار | آیتم بدون مجوز را نشان نمی‌دهد | ❌ خیر (فقط UX) |
| Middleware `permission:` | هر Route را بررسی می‌کند | ✅ **بله** |
| Policy در کنترلر | رکورد مشخص را بررسی می‌کند | ✅ **بله** |

**موجود و درست:** هر ۲۰ مسیر محافظت‌شده `permission:` دارند. این الگو باید در
۲۶ صفحهٔ جدید **بدون استثنا** تکرار شود.

## ۷. Breadcrumb — قاعده

فقط در صفحات عمق ≥۳ سطح:
`داشبورد / پروژه‌ها / پروژهٔ سئو شرکت نمونه / دسترسی‌ها`

در فهرست‌های سطح اول (مشتریان، قراردادها) breadcrumb **نمی‌گذاریم** — ارزش افزوده ندارد.

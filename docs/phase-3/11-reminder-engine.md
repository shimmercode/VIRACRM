# 11 — موتور یادآوری و زمان‌بندی (Gate A)

**Vira CRM** · Gate A · ۲ آذر ۱۴۰۵

این ماژول **هستهٔ عملیاتی** محصول است. اگر یادآوری کار نکند، مدیر فاکتور را دیر
می‌فرستد و گزارش سئو دیر تحویل می‌شود — که طبق سند مرجع §12 هدف اصلی CRM است.

---

## ۱. آنچه امروز هست

| جزء | وضعیت | شاهد |
|-----|--------|------|
| قاعدهٔ «۲ روز تقویمی قبل» | ✅ **اثبات‌شده** | `ReminderScheduleTest` — ۴۳ اَسِرشِن |
| اثبات مستقل «نه ۴۸ ساعت» | ✅ | `docs/src/d2-daymath-verify.php` |
| جدول `scheduled_events` با `unique_key` | ✅ | migration |
| جدول `job_runs` برای observability | ✅ | migration |
| Job / Command که آن‌ها را اجرا کند | ❌ **هیچ** | `routes/console.php` فقط `inspire` |
| cron روی هاست | ❌ **نامعلوم** | H-15 |

**یعنی: منطق درست نوشته و تست شده، ولی هرگز اجرا نمی‌شود.** این را نباید
«پیاده‌شده» شمرد.

## ۲. قاعدهٔ کسب‌وکار (از سند مرجع §5-2، §12، §14)

```
یادآوری فاکتور:  دقیقاً ۲ روز تقویمی قبل از موعد
یادآوری گزارش:   دقیقاً ۲ روز تقویمی قبل از موعد
روز موعد:        یادآور «امروز»
پس از موعد:      تا انجام‌نشدن، «عقب‌افتاده» می‌ماند
```

**تفسیر قطعی «۲ روز تقویمی»:** اگر موعد = ۱۴۰۵/۰۹/۱۰، یادآور در **۱۴۰۵/۰۹/۰۸**.
نه «۴۸ ساعت قبل» (که با DST یا ساعت اجرا جابه‌جا می‌شود).

**تأیید ریاضی مستقل:**
```
موعد: ۳۱ فروردین → ۲ روز قبل = ۲۹ فروردین
موعد: ۱ اردیبهشت  → ۲ روز قبل = ۳۰ فروردین (عبور از ماه)
موعد: ۱ فروردین   → ۲ روز قبل = ۲۹ اسفند سال قبل (عبور از سال)
```

## ۳. معماری: سه لایه

```
┌─ لایهٔ ۱: ReminderSchedule (خالص، بدون DB) ────────────┐
│  schedule(dueDate, offsets) → list<date>               │
│  ✅ موجود و تست‌شده (۴۳ اَسِرشِن)                       │

                     ▼
┌─ لایهٔ ۲: ReminderEngine (مصرف‌کننده، با DB) ──────────┐

                     ▼
┌─ لایهٔ ۳: Scheduler (اجرا) ────────────────────────────┐
│  vira:reminders:run  (Artisan Command)                 │
│  ثبت در job_runs                                       │
└────────────────────────────────────────────────────────┘
```

## ۴. Idempotency — کلید درست

`unique_key` = `{event_type}:{event_id}:{kind}:{fire_date}`

```
نمونه: invoice:42:due_soon:2026-02-28
       invoice:42:due_today:2026-03-02
       report:88:due_soon:2026-03-05
```

| سناریو | نتیجه |
|--------|-------|
| اجرای دوبارهٔ همان روز | `updateOrCreate` → **همان ردیف**، نه ردیف دوم ✅ |
| تغییر موعد از ۰۹/۱۰ به ۰۹/۱۵ | ردیف‌های قدیمی حذف، ردیف‌های ۱۳/۰۹ و ۱۵/۰۹ ساخته ✅ |
| اجرا در دو سرور هم‌زمان | `unique` constraint روی DB مانع تکرار ✅ |
| Job نیمه‌کار بماند | تراکنش rollback ✅ |

## ۵. استقلال فاکتور و گزارش — الزام صریح

سند §12 می‌گوید: «یک فاکتور انجام‌شده نباید یادآور گزارش را ببندد».

پیاده‌سازی:
- `project_events.kind` = `invoice` | `report`
- `unique_key` شامل `event_type` است → دو مجموعهٔ مستقل
- `state` روی خود رویداد است، نه روی یادآور → تکمیل یکی، دیگری را تغییر نمی‌دهد
- تست اختصاصی: تکمیل فاکتور → `report` یادآور **باز** می‌ماند

## ۶. سه سناریوی اجرا بر اساس واقعیت هاست (H-15)

### سناریو A — cron روزانه موجود ✅ (ترین حالت)

```php
Schedule::command('vira:reminders:run')->dailyAt('08:00')->timezone('Asia/Tehran');
```
یک اجرا در روز کافی است چون `kind`‌ها تاریخ‌محورند. «عقب‌افتاده» با `fire_date < today`
به‌صورت کوئری محاسبه می‌شود، نه Job جدید.

### سناریو B — cron با حداقل ۵ دقیقه

```php
->everyFiveMinutes()
```
`job_runs` بررسی می‌کند «امروز اجرا شده؟» و اگر بله، فوراً خارج می‌شود.

### سناریو C — بدون cron ❌ (بدترین حالت)

**Fallback صادقانه:**
```php
// middleware سبک، پس از پاسخ (terminating)
if (lastRunAt() < now()->subHour()) {
    dispatch(fn () => Artisan::call('vira:reminders:run'))->afterResponse();
}
```

**محدودیت صریح که باید کتباً اعلام شود:**
> اگر هیچ‌کس به سیستم وارد نشود، یادآوری ساخته نمی‌شود. برای CRM داخلی که
> مدیر روزانه وارد می‌شود این در عمل کافی است، ولی **تضمین SLA ندارد**.

**تصمیم نهایی منوط به H-15 است (OD-07).**

## ۷. مرز روز و Timezone — تصمیم لازم

| سؤال | گزینه‌ها | پیشنهاد |
|------|----------|---------|
| Timezone | `Asia/Tehran` ثابت | ✅ **توصیه** — کاربران ایرانی‌اند |
| ساعت اجرا | ۰۰:۰۱ / ۰۸:۰۰ / ۱۸:۰۰ | **۰۸:۰۰** — مدیر اول صبح کارتل را می‌بیند |
| مرز روز | نیمه‌شب تهران | ✅ |
| DST | ایران DST ندارد (از ۱۴۰۱ حذف شد) | ولی کد نباید به آن وابسته باشد |

**قاعده:** محاسبهٔ تاریخ **همیشه** روی `date` (بدون ساعت) انجام می‌شود تا تغییر
ساعت اجرا، `fire_date` را جابه‌جا نکند.

## ۸. وضعیت‌های کارتل

| `kind` | شرط | نمایش |
|--------|-----|-------|
| `due_soon` | `fire_date = today` و `due_date > today` | «۲ روز مانده» |
| `due_today` | `due_date = today` | «امروز» |
| `overdue` | `due_date < today` و `state != done` | «X روز گذشته» — **هرگز پنهان نمی‌شود** |
| `done` | `state = done` | در «انجام‌شده» (تاریخچه) |

**قاعدهٔ سخت سند §2:** «موارد عقب‌افتاده تا زمان تعیین تکلیف در کارتابل باقی بمانند».
پس `overdue` بدون حد زمانی نمایش داده می‌شود — نه اینکه بعد از ۳۰ روز پنهان شود.

## ۹. ساختار داده (موجود و تأییدشده، بدون تغییر)

**تأیید شد:** رویدادهای فاکتور و گزارش در جدول **`work_items`** هستند، نه یک جدول
جداگانه. این را با خواندن migration تأیید کردم:

```
work_items            ← رویداد فاکتور/گزارش  (kind: invoice|report, due_date, period, state)
                        ✅ ۹ ردیف داده دارد — تنها بخش کارتل که واقعاً داده دارد
scheduled_events      ← یادآور تولیدشده (unique_key, kind, fire_date)
job_runs              ← ثبت هر اجرا (job, status, processed, created, failed)
```

**طراحی درست است:** یک جدول `work_items` با ستون `kind` هر دو نوع را نگه می‌دارد
و `scheduled_events` جداگانه یادآورها را ثبت می‌کند. تفکیک «رویداد» از «یادآور»
درست است — یک رویداد می‌تواند چند یادآور داشته باشد (D-2، روز موعد، عقب‌افتاده).

**پس هیچ جدول جدیدی برای رویدادها لازم نیست.** Model `WorkItem` نیز موجود است.

**تنها شکاف:** `WorkItem` هیچ Route/View ندارد — ۹ ردیف داده در داشبورد خوانده
می‌شود ولی مدیر نمی‌تواند آن‌ها را ایجاد/ویرایش/انجام کند.

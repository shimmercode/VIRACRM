# معماری VIRA CRM

**وضعیت:** Modular Monolith · Laravel 12 · Blade SSR

---

## ۱. تصمیم بنیادین

**Modular Monolith** — یک اپلیکیشن، مرزهای ماژولار داخلی.

| گزینهٔ ردشده | دلیل |
|--------------|------|
| Microservices | تیم کوچک، یک هاست اشتراکی، پیچیدگی عملیاتی بی‌توجیه |
| Repository Pattern | لایهٔ انتزاع بی‌ارزش روی Eloquent |
| CQRS / Event Sourcing | پیچیدگی برای دامنهٔ CRUD محور |
| Livewire / Inertia | وابستگی سمت کلاینت بدون نیاز اثبات‌شده |
| Tailwind | سیستم طراحی اختصاصی موجود است |
| SPA | SEO لازم نیست، ولی سرعت اولیه و سادگی مهم است |

**اصل:** هر انتزاع باید یک درد واقعی را حل کند. هیچ‌کدام از موارد بالا نمی‌کند.

## ۲. لایه‌ها

```
┌──────────────────────────────────────────────┐
│  HTTP (routes/web.php)                        │  ۲۲ مسیر
│  middleware: auth · permission · throttle     │
├──────────────────────────────────────────────┤
│  Controllers (thin)                           │  اعتبارسنجی + فراخوانی
├──────────────────────────────────────────────┤
│  Form Requests      │  Services              │
│  اعتبارسنجی متمرکز  │  منطق دامنه            │
├──────────────────────────────────────────────┤
│  Models (Eloquent)                            │  ۱۸ مدل
│  Scope · Cast · Relation                      │
├──────────────────────────────────────────────┤
│  Support (JalaliDate · Money · PersianNumber) │  بدون وابستگی به HTTP
├──────────────────────────────────────────────┤
│  MySQL / SQLite                               │
└──────────────────────────────────────────────┘
```

**قاعده:** Controller هرگز کوئری نمی‌سازد. Service هرگز `Request` نمی‌بیند.

## ۳. سرویس‌های موجود

| سرویس | مسیر | وضعیت واقعی |
|-------|------|-------------|
| `AuditRecorder` | `Services/Security/` | ✅ **متصل** — ۲۳۲ ردیف |
| `EnvelopeEncrypter` | `Services/Security/` | ⚠️ **متصل نیست** — واحد تست دارد |
| `PermissionCatalog` | `Services/Security/` | ✅ متصل |
| `ReminderSchedule` | `Services/Reminders/` | ⚠️ **متصل نیست** |
| `Labels` | `Services/I18n/` | ✅ متصل |

**این تفکیک «ساخته‌شده» از «فعال» مهم است.** دو سرویس تست واحد دارند اما هرگز
در مسیر درخواست اجرا نمی‌شوند. تست واحدِ سبز به‌معنای کارکردن نیست.

## ۴. قرارداد تراکنش

پنج عملیات **باید** درون `DB::transaction` باشند:

| عملیات | چرا |
|--------|-----|
| ایجاد قرارداد + نسخهٔ اول | دو جدول |
| تغییر وضعیت قرارداد + Audit | وضعیت باید با ردپا هم‌گام باشد |
| ایجاد پروژه + تخصیص‌ها | چند جدول |
| ثبت سند حسابداری + خطوط | توازن باید اتمی باشد |
| چرخهٔ یادآوری + `scheduled_events` | ایجاب‌کردن یکتا |

**بدون تراکنش، یک خطای میانی داده نیمه‌کاره می‌گذارد** — که در قرارداد و
حسابداری فاجعه است.

## ۵. تاریخ شمسی

| قاعده | پیاده‌سازی |
|-------|-----------|
| ذخیره | میلادی (`DATE`) |
| نمایش | شمسی (`JalaliDate`) |
| ورودی کاربر | شمسی → میلادی در Form Request |
| مرتب‌سازی/فیلتر | میلادی |
| Audit | میلادی + شمسی در نمایش |

**هرگز تاریخ شمسی رشته‌ای در DB ذخیره نمی‌شود** — مقایسه و مرتب‌سازی می‌شکند.

## ۶. پول

```
DB: BIGINT (ریال)
Support\Money: wrapper با تبدیل صریح
UI: تومان با برچسب صریح "تومان"
```

**بدون float، بدون decimal، بدون تبدیل خودکار.** `Money` تنها راه مجاز است.

---

## ۷. مرز ماژول‌ها (هدف)

```
app/Modules/  (پیشنهادی آینده — نه الان)
  Customers/   Contracts/   Projects/   Credentials/
  Reminders/   Accounting/  Payroll/    Reports/
```

**اکنون این کار انجام نمی‌شود.** بازسازی ساختار موجود بدون دلیل، ریسک است.
مرزها در نام‌گذاری و لایه‌بندی رعایت می‌شوند؛ جابه‌جایی فیزیکی وقتی لازم می‌شود
که یک ماژول واقعاً بزرگ شود.

## ۸. آنچه عمداً نیست

- ❌ صف واقعی (queue) — همه چیز sync تا نیاز اثبات شود
- ❌ WebSocket — هیچ نیاز realtime تأیید نشده
- ❌ API عمومی — هیچ مصرف‌کنندهٔ خارجی
- ❌ Multi-tenancy — یک سازمان
- ❌ Feature flags — پیچیدگی بی‌مصرف

# VIRA CRM — گزارش سازگاری هاست (فاز ۰)

| مورد | مقدار |
|---|---|
| تاریخ گزارش | 2026-11-22 |
| دامنه هدف | `crm.viraagency.co` |
| IP | `185.164.72.77` (مشترک با `viraagency.co` و `www.viraagency.co`) |
| منبع بررسی | sandbox توسعه (شبکه با محدودیت خروج) |
| وضعیت کلی | **CHECK NOT COMPLETED — نیازمند اجرای اسکریپت روی هاست توسط کارفرما** |

> **این گزارش، «گزارش بررسی هاست» به معنای تأیید سازگاری نیست.** تیم مهندسی به SSH، cPanel،
> FTP یا کنسول هاست دسترسی ندارد. هر عددی که در این سند به‌عنوان «تأییدشده» علامت نخورده،
> فرض یا نامعلوم است و نباید مبنای تصمیم قطعی شود.

| H-02 | رزولوشن DNS سایت اصلی | **تأییدشده** — `viraagency.co → 185.164.72.77` | `getent hosts` |

### تفسیر H-05/H-06 (مهم)

عدم توفیق TLS از این sandbox **به‌معنای خرابی SSL سایت نیست**؛ به احتمال زیاد شبکه sandbox محدود
است یا سرور اتصال‌های منابع ناشناس را می‌بندد. برای تصمیم‌گیری امنیتی، **نباید** این را خطای
هاست تلقی کرد. کارفرما باید از طریق مرورگر/ابزار داخلی وضعیت SSL ساب‌دامین را تأیید کند.

## ۳) روش بررسی توسط کارفرما (۵ دقیقه)

1. فایل `docs/tools/host-compatibility-check.php` را با FTP در پوشه‌ای محافظت‌شده روی ساب‌دامین
   CRM آپلود کنید (بهتر است پوشه با Basic Auth محافظت شود).
2. متغیر محیطی `VIRA_DIAG_TOKEN` را (اگر از طریق پنل ممکن است) روی یک مقدار تصادفی تنظیم کنید،
   یا توکن را داخل فایل تغییر دهید.
3. آدرس `https://crm.viraagency.co/_diag/host-check.php?token=...` را باز کنید و خروجی را برای تیم بفرستید.
4. برای بررسی DB، متغیرهای `VIRA_DB_HOST`, `VIRA_DB_NAME`, `VIRA_DB_USER`, `VIRA_DB_PASS` را
   در محیط تنظیم کنید (یا از SSH با `php host-compatibility-check.php --text` اجرا کنید).
5. **پس از دریافت گزارش، فایل و پوشه `_diag` را حذف کنید.**

> اسکریپت هیچ رمزی را ذخیره یا چاپ نمی‌کند و فقط نام/نسخه/فعال‌بودن ماژول‌ها را گزارش می‌دهد.

## ۴) تصمیم‌های وابسته

| اگر | آنگاه |
|---|---|
| PHP ≥ 8.3 تأیید شد | پیشنهاد ارتقا به Laravel 13 در ADR (تصمیم با کارفرما) |
| PHP = 8.2 | Laravel 12 همان‌طور که در ADR-0001 آمده |
| PHP < 8.2 | **توقف و ارجاع به کارفرما**؛ گزینه‌ها در بخش ۶ ADR-0001 |
| Cron موجود نیست | External cron روی endpoint امضاشده + مستندسازی ریسک |
| Document Root مستقل ممکن نیست | ساختار `public_html` با `.htaccess` سخت‌گیرانه + جابه‌جایی `.env` به بیرون |
| SSL موجود نیست | **ماژول دسترسی‌ها تا تأمین SSL فعال نمی‌شود** |

## ۵) نتیجه‌گیری

- **هیچ ادعایی دربارهٔ سازگاری هاست مطرح نیست.**
- سازگاری Laravel با هاست **تأییدنشده** و در وضعیت **BLOCKED** است (تست `T-INF-01`).
- پلن اجرایی: اجرای اسکریپت توسط کارفرما → تثبیت ADR-0001 → شروع فاز ۳.

## ۹) بازبینی و بازنویسی اسکریپت بررسی (2026-11-22)

در بازبینی دوم، دو نقص واقعی در اسکریپت قبلی پیدا و رفع شد:

### ۹.۱ نقص اول — خطای نحوی روی هاست قدیمی (بحرانی)

نسخه قبلی از **arrow function** (`fn (...) =>`) استفاده می‌کرد که فقط از PHP **7.4**
پشتیبانی می‌شود. اگر هاست PHP 7.2 یا 7.3 داشت — که **دقیقاً همان حالتی است که این
اسکریپت برای کشفش ساخته شده** — فایل با `Parse error` متوقف می‌شد و **هیچ اطلاعاتی
تولید نمی‌کرد**. یعنی ابزار در مهم‌ترین سناریو، کور بود.

| مورد | نسخه قبلی | نسخه جدید |
|---|---|---|
| نگارش نحوی | PHP 7.4+ (arrow fn) | **PHP 5.6+** (بدون `fn`، `??`، typed property، `catch (Throwable)`) |
| شاهد | ۲ مورد `fn (` در نسخه commit شده | اسکن خودکار: CLEAN |

### ۹.۲ نقص دوم — هیچ بررسی cron/scheduler نداشت

تعداد بررسی‌های cron در نسخه قبلی: **صفر**. در حالی که بدون cron، یادآور D-2 و یادآور
گزارش سئو **قابل اجرا نیستند** و این یکی از سه ریسک اصلی پروژه است.

### ۹.۳ آنچه اکنون بررسی می‌شود (۱۰۲ بررسی)

اعداد زیر **شمارش واقعی خروجی JSON** هستند (اجرا در sandbox، `checks=102`):

| گروه | نمونه موارد | تعداد |
|---|---|---|
| `php` | نسخه، SAPI، معماری، حافظه، `max_execution_time`، آفست زمانی، cipherها، توابع غیرفعال | ۲۸ |
| `ext` | ۲۱ افزونه ضروری + ۴ اختیاری | ۲۵ |
| `cron` | `/etc/crontab`، `/etc/cron.d`، `/var/spool/cron`، `crontab -l`، `systemctl`، قابلیت اجرا | **۱۱** |
| `sec` | `display_errors`، `expose_php`، `allow_url_include`، کوکی نشست، `file_uploads`، مسیر سشن | ۱۲ |
| `fs` | Document Root، قابل‌نوشتن بودن temp، فضای دیسک، `open_basedir` | ۱۰ |

### ۹.۴ قواعد ایمنی که رعایت شده (راستی‌آزمایی شده)

| قاعده | شاهد |
|---|---|
| فقط-خواندنی | اسکن کد: هیچ `file_put_contents`/`unlink`/`mkdir`/`DDL`/`DML` | 
| توکن در حالت وب | `hash_equals` + الزام تغییر `CHANGE_ME_BEFORE_UPLOAD` → بدون تغییر، همیشه `403` |
| هیچ رمزی در فایل | اتصال DB فقط از `VIRA_DB_*` محیطی؛ پیام خطا فقط **نوع** استثنا را می‌گوید |
| خروجی JSON معتبر | اعتبارسنجی `json_encode`/`json_decode` پیش از چاپ؛ تست واقعی: `checks=102`, JSON valid |
| حریم خصوصی crontab | فقط **تعداد خطوط** گزارش می‌شود، نه محتوای وظایف |
| پس از استفاده حذف شود | در `next_steps` خروجی و در چک‌لیست انتشار |

### ۹.۵ چیزی که با این بازنویسی **تغییر نکرده**

> ⚠️ **سازگاری هاست همچنان تأیید نشده است.** نتیجه اجرا در sandbox
> (`LIKELY_COMPATIBLE_WITH_WARNINGS`) **بی‌معنا برای هاست واقعی** است، چون:
> - PHP-WASM است، نه PHP نصب‌شده روی `185.164.72.77`
> - Composer در sandbox نیست (هشدار `composer_available`)
> - Cron در sandbox شبیه‌سازی نمی‌شود
> - MySQL واقعی وجود ندارد (اتصال skip شد)
>
> این خروجی فقط **آزمون خود اسکریپت** است: «آیا کد اجرا می‌شود، JSON معتبر می‌دهد و
> رفتار محافظه‌کارانه دارد؟» — پاسخ: بله. تأیید سازگاری هاست همچنان **BLOCKED** است
> تا خروجی **واقعی** از `crm.viraagency.co` برسد (OD-01).

## ۲. ممیزی امنیت Credentials

### مدل مجوز

سه قدرت جدا، و `User::hasPermission()` **تطبیق دقیق کد** است — هیچ wildcard،

| مجوز | نقش‌ها | معنا |
|---|---|---|
| `credentials.view` | manager, account_manager | دیدنِ اینکه دسترسی وجود دارد |
| `credentials.manage` | manager, account_manager | ایجاد/ویرایش/حذف ردیف |
| `credentials.reveal` | manager | خواندنِ یک رمز از پشت رمزنگاری |

`account_manager` عمداً view+manage دارد و نه reveal و نه export: کسی که
دسترسی‌ها را ثبت می‌کند لزوماً کسی نیست که باید رمزها را بخواند.

### آنچه دربارهٔ رمزنگاری ثابت شد

| مورد | نتیجه |
|---|---|
| ذخیرهٔ رمز | `v1:` envelope ciphertext، حاوی plaintext نیست (T-CEA-02) |
| الگوریتم | AES-256-GCM، nonce ۹۶ بیتی تصادفی برای هر رکورد |
| نبودِ کلید | `store()` **قبل از نوشتن** استثنا می‌دهد — fail closed |
| نشت در گزارش | صفر ردیف audit حاوی plaintext (T-CEA-04) |
| نشت در DOM | `credential-shots` در سوئیت کامل |

### دو نکته دربارهٔ خودِ این آزمون

1. **تست‌های منفی اول ۴۱۹ می‌دادند، نه ۴۰۳** — یعنی روی CSRF شکست می‌خوردند نه
   روی مجوز. این «سبز به دلایل غلط» بود: اگر همان‌طور رها می‌شد، یک باگ CSRF
   می‌توانست به‌جای یک باگ دسترسی، این تست‌ها را قرمز کند و برعکس. حالا هر عامل
   توکن را از داشبورد می‌گیرد (viewer که `credentials.view` ندارد و نمی‌تواند
   صفحهٔ حامل فرم خروجی را بخواند).
2. **T-CEA-11 اول `select 1 == 1` بود** — یعنی هیچ چیز نمی‌سنجید. حالا بین دو
   خروجی، `storage/` را برای PDF جاروب می‌کند. اگر روزی خروجی روی دیسک کش شود،
   این تست قرمز می‌شود — و فایلِ کش‌شدهٔ محرمانه دقیقاً همان چیزی است که به
   انقضا نیاز پیدا می‌کند.

### ریسک باقی‌مانده در این بخش

`credentials.export` به نقش `manager` داده شد چون `credentials.reveal` هم دارد و
جدا ماندنش یعنی عملاً هیچ‌کس جز ابرمدیر نمی‌توانست خروجی بگیرد. **اما این یک
تصمیم دسترسی است، نه یک واقعیت فنی.** اگر در سازمان شما مدیر نباید رمزها را
بیرون ببرد، این گرنت باید برداشته شود و export فقط به ابرمدیر برسد. منتظر
تصمیم شما.

## ۳. ممیزی Backup & Restore

### وضعیت فعلی

**صفر کد بکاپ.** جدول `backup_runs` ساخته نشده، هیچ فرمان کنسولی نیست، هیچ
آزمون بکاپی وجود ندارد. دو مورد یافت‌شده با `grep -i backup` در `app/` فقط
کلمهٔ «backup» در کامنت‌اند.

### محدودیت‌های واقعی هاست (از `docs/HOST_COMPATIBILITY.md`)

| محدودیت | وضعیت | پیامد برای بکاپ |
|---|---|---|
| SSH | **BLOCKED** | هیچ اسکریپت shell سمت سرور |
| Cron | **BLOCKED** | زمان‌بندی خودکار درون‌سروری ممکن نیست |
| `exec` | ممکن است غیرفعال باشد | `sqlite3 .backup` و `tar` قابل اتکا نیستند |
| `max_execution_time` | ≥۶۰s، **NOT TESTED** | بکاپ بزرگ ممکن است وسط کار قطع شود |
| حافظه | محدود | بارگذاری کل DB در حافظه نه |

**نتیجهٔ مهم:** معماری بکاپ نباید به shell، cron سمت سرور، یا `exec` وابسته
باشد. این یک محدودیت طراحی است، نه ترجیح.

### معماری پیشنهادی

| لایه | طرح | چرا این |
|---|---|---|
| **Database** | `SQLite3::backup()` از طریق PDO/PHP — معادل `sqlite3 .backup`، بدون shell | آنلاین و امن روی DB در حال نوشتن؛ `exec` لازم ندارد |
| **File** | پیمایش PHP روی `storage/app` + `ZipArchive` | بدون `tar` |
| **Encryption** | AES-256-**GCM** با `openssl_encrypt`، نه CBC | GCM اصالت‌دار است؛ در بخش ۳.۳ ثابت شد چرا CBC کافی نیست |
| **Integrity** | مانیفست SHA-256 برای **هر** فایل، بررسی **قبل از** بازیابی | تنها کنترل قطعی؛ در ۳.۳ ثابت شد |
| **Off-site** | انتقال با cURL به فضای خارجی (S3-سازگار یا WebDAV) | cURL معمولاً حتی وقتی `exec` بسته است باز است |
| **Retention** | روزانه ۷، هفتگی ۴، ماهانه ۶ — حذف خودکار پس از آپلود موفق | بدون این، فضا پر می‌شود و بکاپ متوقف می‌شود |
| **Scheduling** | چون cron سمت سرور BLOCKED است: **پینگ خارجی** (یک سرویس زمان‌بند بیرونی به یک مسیر امضاشده) + `after-response` به‌عنوان fallback | تنها راه بدون cron |
| **Restore** | فرمان `vira:restore` که اول مانیفست را می‌سنجد، بعد در مسیر موقت باز می‌کند، `integrity_check` می‌گیرد، و **فقط پس از موفقیت** جایگزین می‌کند | بازیابی نیمه‌تمام بدتر از نبودِ بازیابی است |

### ۳.۳ آنچه واقعاً اجرا و ثابت شد

یک چرخهٔ کامل بکاپ → رمزنگاری → بازیابی → اعتبارسنجی در محیط تست انجام شد.
**پایگاه دادهٔ مبدأ فقط خوانده شد** (`mode=ro`) و پس از پایان، دست‌نخورده تأیید
شد (۲۳۲ ردیف audit، ۲ کاربر، `integrity_check: ok`).

**بکاپ:**

| قلم | مقدار |
|---|---|
| جداول | ۵۷ |
| ردیف‌ها | ۴۸۲ |
| `integrity_check` مبدأ | ok |
| `foreign_key_check` مبدأ | ۰ تخلف |
| اندازهٔ DB | ۸۴۷٬۸۷۲ بایت |
| `storage/app` | ۸ عضو |
| رمزنگاری | AES-256-CBC + pbkdf2 ۲۰۰٬۰۰۰ تکرار |

**بازیابی در دایرکتوری تمیز:**

| بررسی | نتیجه |
|---|---|
| `PRAGMA integrity_check` | **ok** |
| `PRAGMA foreign_key_check` | **۰ تخلف** |
| جداول بازیابی‌شده | ۵۷ (مطابق مانیفست) |
| ردیف‌های بازیابی‌شده | ۴۸۲ (مطابق مانیفست) |
| تفاوت در تعداد ردیف | **هیچ — هر ۵۷ جدول مطابقت کرد** |
| **هش محتوای هر ۵۷ جدول** | **۰ تفاوت** — نه فقط شمارش، محتوا |
| خواندن رکورد واقعی | `VIRA-C-1404-0001`، ۱۶۸ رویداد login، ۵۵ مجوز، ۸۱ role_permission |

**آزمون دست‌کاری — و یک یافتهٔ مهم:**

```
openssl روی فایل دست‌کاری‌شده: exit 0   ← CBC هیچ اصالت‌سنجی ندارد
manifest sha256: 6d592d01fcc8436614082afe…
restored sha256: fcf368af5cd1c7f9c7024093…
VERDICT: MISMATCH — بازیابی به‌درستی رد شد
```

**AES-256-CBC اصالت‌سنجی ندارد.** فایل دست‌کاری‌شده بدون خطا رمزگشایی شد. این
یک واقعیت رمزنگاری دربارهٔ CBC است، نه یک باگ در پیاده‌سازی.

**اما یک ادعای اولیهٔ خودم را اصلاح می‌کنم:** اول نوشتم «بکاپ دست‌کاری‌شده بی‌صدا
بازیابی می‌شود و سالم به نظر می‌رسد». این را **اثبات نکردم**. ۲٬۲۴۴ آفست
رمزگشایی‌شدنی را پیمایش کردم تا حالتی پیدا کنم که `integrity_check` مقدار `ok`
بدهد و داده عوض شده باشد — **پیدا نشد**. دست‌کاری‌ها یا پرصدا بودند (DB باز
نمی‌شد) یا در فضای آزاد SQLite می‌افتادند (هیچ داده‌ای عوض نمی‌شد). پس:

- در برابر **خرابی تصادفی**، «openssl موفق + integrity_check ok» در عمل کافی
  به نظر می‌رسد.
- در برابر **حملهٔ عمدی** کافی **نیست**: CBC انعطاف‌پذیر است و مهاجمی که بتواند
  بیت‌های ciphertext را عوض کند، می‌تواند تغییر تک‌بیتیِ انتخابی در بلوک بعدی
  ایجاد کند. پیمایش کورِ من چنین آفستی نیافت، و این محدودیتِ جست‌وجوست نه اثباتِ
  امنیت.
- چون مانیفست SHA-256 هزینه‌اش ناچیز و تضمینش قطعی است، **الزامی** است.

2. **Off-site واقعی آزموده نشد** — مقصد خارجی در دسترس نبود.
3. **زمان‌بندی آزموده نشد** — cron در این محیط نیست.
4. **بازیابیِ زیر بار آزموده نشد.**
5. **`storage/app` عملاً خالی است** (۰ پیوست) — پس «بکاپ فایل» امروز چیز واقعی
   برای اثبات ندارد. به محض اولین آپلود جدی می‌شود.

## ۴. Audit Log

### مجوز `audit.view`

| بررسی | نتیجه |
|---|---|
| در جدول `permissions` | **هست** |
| داده شده به نقشی | **نه — صفر نقش** |
| استفاده در `app/` | **هیچ** |
| استفاده در `routes/` | **هیچ** |
| مسیر با `audit` در URI | **هیچ** |
| فایل Blade مرتبط | **هیچ** |

**یعنی داده جمع می‌شود ولی هیچ راه خواندنی ندارد.** تنها راه فعلی، کوئری مستقیم
به پایگاه داده است. این یک شکاف باز است، نه یک تصمیم.

### پوشش رویدادها (الزام کارفرما)

۱۵ کنترلر `AuditRecorder` را صدا می‌زنند و همهٔ موجودیت‌های خواسته‌شده پوشش
دارند:

| رویداد خواسته‌شده | پوشش | اثبات اجرایی |
|---|---|---|
| ورود | `LoginController` | ۱۶۸ ردیف `login` در DB |
| خروج | `LoginController` | ۷ ردیف `logout` |
| ورود ناموفق | `LoginController` | ۱۱ ردیف `login_failed` |
| تغییر مشتری | `CustomerController` | `created`/`updated` |
| تغییر قرارداد | `ContractController` | `subject_type = App\Models\Contract` |
| تغییر پروژه | `ProjectController` | پوشش دارد |
| دسترسی‌ها | `CredentialController` | `revealed` — `T-CRD-10` |
| اعتبارنامه‌ها | `CredentialController` | `created`/`updated`/`deleted` |
| Export | `ExportController` | `exported` — **T-CEA-03 (۰→۱)** |
| تلاش غیرمجاز | `EnsurePermission` | ۲۷ ردیف `denied` |

### نشت اطلاعات حساس

`AuditLog::redact()` در `AuditRecorder::record()` اجرا می‌شود — یعنی **بعد از**
ساخت تغییرات و **قبل از** نوشتن. هر کلیدی که یکی از این تکه‌ها را داشته باشد
`[redacted]` می‌شود:

```
password, passwd, secret, token, api_key, apikey, ciphertext,
private_key, encryption_key, remember_token, credential,
authorization, cookie
```

آزمون: `tests/Feature/AuthorizationTest.php:166-181` — `password`،
`password_confirmation`، `api_key`، `remember_token` و `nested.credentials` همه
`[redacted]`، در حالی که `company_name` و `nested.city` سالم می‌مانند.
علاوه بر آن **T-CEA-04** اثبات کرد هیچ ردیف audit حاوی plaintext رمز نیست.

### طراحی پیشنهادی صفحهٔ Audit Log

**مسیر:** `GET /audit` با `permission:audit.view`
**چرا این مجوز و نه `reports.view`:** گزارش رویداد شامل نام کاربری، IP و
user-agent همهٔ کاربران است — از جمله ابرمدیر. کسی که گزارش مالی می‌بیند نباید
لازم باشد رفتار ابرمدیر را ببیند.

| بخش | محتوا |
|---|---|
| ستون‌ها | زمان شمسی، کاربر، رویداد، نوع موجودیت، شناسه، IP، توضیح |
| فیلترها | بازهٔ تاریخ، کاربر، نوع رویداد، موجودیت |
| جزئیات | `changes` با مقدار `[redacted]` **همان‌طور که هست** — نه حذف، تا مشخص باشد چیزی پوشانده شده |
| مرتب‌سازی | `created_at desc` (ایندکس موجود است) |
| صفحه‌بندی | ۵۰ ردیف — ۲۳۲ ردیف امروز کوچک است ولی رشد می‌کند |
| خروجی | **هیچ** — در نسخهٔ اول. اضافه کردن export به لاگِ امنیتی یعنی افزودن یک راه نشت تازه |

**ایندکس‌های موجود که این صفحه استفاده می‌کند:** `(subject_type, subject_id)`،
`created_at`، `event` — هر سه از قبل ساخته شده‌اند.

**الزام تکمیلی:** خواندنِ خودِ لاگ هم باید ثبت شود (`audit.viewed`)، وگرنه
کسی می‌تواند همهٔ لاگ را بخواند بدون رد پا.

### شکاف‌های باقی‌مانده در Audit

1. **هیچ سیاست نگهداری نیست** — جدول بی‌نهایت رشد می‌کند.
2. **خواندنِ فهرست‌ها ثبت نمی‌شود** — فقط `revealed` و `exported`.
3. **`updated` تنها جایی نوشته می‌شود که کنترلر صریحاً صدا بزند** — پوشش
   سراسری تضمین‌شده نیست.
4. **`personnel.create` و `payroll.approve` هم مثل `audit.view` یتیم‌اند** — در
   جدول مجوزها هستند ولی به هیچ نقشی داده نشده‌اند.

## ۵. API و اتصال آینده به WordPress

### محدودیت فعلی (مستند شد)

`docs/API_DOCUMENTATION.md` صریحاً می‌گوید API وجود ندارد:

| بررسی | نتیجه |
|---|---|
| `routes/api.php` | **نیست** |
| Sanctum / Passport / JWT | **نصب نیست** |
| مسیر با `api` در URI یا نام | **۰ از ۱۰۵** |
| توکن / کلید API / امضای درخواست | **هیچ** |

سطح HTTP موجود: ۵۳ GET، ۳۲ POST، ۱۰ PUT، ۱۰ DELETE — همه مسیر وب لاراول با
احراز هویت کوکی نشست. **API بدون نیاز واقعی پیاده‌سازی نشد.**

### معماری اتصال آینده

| لایه | طرح | نکتهٔ مهم |
|---|---|---|
| **Authentication** | Sanctum با **توکن stateful نه**، بلکه personal access token؛ یا بهتر: کلید سرویس با scope | کوکی نشست برای ماشین مناسب نیست؛ CSRF هم معنا ندارد |
| **Authorization** | همان `permission:*` — ولی با **scope جدا** مثل `api:credentials.read` | مجوز وب نباید خودکار مجوز API باشد |
| **Rate Limiting** | throttle جدا از `throttle:10,1`ِ ورود؛ مثلاً ۶۰/دقیقه به ازای توکن | ورود انسان و ماشین رفتار متفاوت دارند |
| **Versioning** | `/api/v1/...` از روز اول | افزودن نسخه بعداً یعنی شکستن کلاینت |
| **Audit Logging** | همان `AuditRecorder` + ستون منبع (`web`/`api`) | بدون این، نمی‌شود فهمید چه چیزی از API آمده |
| **Secure Integration** | IP allowlist + HTTPS اجباری + `X-Content-Type-Options` موجود | وردپرس و CRM باید هر دو پشت TLS باشند |

### نکتهٔ امنیتی خاص اتصال وردپرس

وردپرس در این محصول یک **اعتبارنامهٔ ذخیره‌شده** است (`credential_types.code =
wordpress`). اگر API ساخته شود، **بدیهی‌ترین و خطرناک‌ترین اشتباه** این است که
endpointی ساخته شود که این رمزها را به وردپرس برگرداند — یعنی CRM بشود یک
سرور توزیع رمز.

پیشنهاد صریح: **API هیچ‌وقت `credentials.*` را برنگرداند.** اگر وردپرس به داده
نیاز دارد، دادهٔ غیرمحرمانه (وضعیت پروژه، فاکتور) برگردانده شود. رمزها باید
دستی و از راه همان صفحهٔ موجود منتقل شوند، چون آن صفحه `reveal` و `export` را
جدا نگه می‌دارد و هر دو را ثبت می‌کند.

## ۶. اصلاح ابهام گزارش (بند ۶)

گزارش قبلی می‌گفت «۹ کلاس بدون استایل» و بعد «۵ مورد خطای نام در markup» — ولی
فقط ۴ مورد فهرست کرده بود، و ۲+۵+۱+۲ = ۱۰ می‌شد نه ۹. **عدد با فهرست خودش
نمی‌خواند.**

جدول درست (در `docs/REGRESSION_TEST_REPORT.md` اصلاح شد):

| # | توکن گزارش‌شده | دسته | رخداد | اقدام |
|---|---|---|---:|---|
| ۱ | `.v-input--invalid'` | مثبت کاذبِ اسکنر | — | باگ اسکنر رفع شد |
| ۲ | `.v-textarea--invalid'` | مثبت کاذبِ اسکنر | — | همان باگ (یک ریشه) |
| ۳ | `.v-badge--warn` | نام غلط | ۴ در ۴ فایل | → `--warning` |
| ۴ | `.v-form__actions` | نام غلط | ۴ در ۴ فایل | → `v-formactions` |
| ۵ | `.v-field__label` | نام غلط | ۳۲ در ۵ فایل | → `v-label` |
| ۶ | `.v-muted-sm` | نام غلط | ۱ | → `v-muted v-small` |
| ۷ | `.v-card--danger` | **واقعاً نبود** | ۱ | قاعدهٔ CSS تعریف شد |
| ۸ | `.item-row` | hook جاوااسکریپت | ۱ | معافیت (app.js:412) |
| ۹ | `.line-total` | hook جاوااسکریپت | ۱ | معافیت (app.js:438) |

**۹ توکن یکتا** = ۲ مثبت کاذب (یک باگ) + ۴ نام غلط (**۴۱ رخداد**) + ۱ قاعدهٔ
غایب + ۲ hook. پس «۹ ایراد» در واقع **۵ تغییر کد** بود.

شمارش‌ها از خودِ کامیت `32b3ba4` استخراج شد، نه از حافظه. یک تصحیح دیگر:
`v-badge--warn` با `grep` ساده ۲۵ می‌داد چون `--warning` هم با آن پیشوند
می‌خواند؛ شمارش دقیق با Python **۴** است (۲۱ استفادهٔ دیگر `--warning` درست
داشتند).

همچنین پیام کامیت `4efc6ce` می‌گوید «Five were markup using a name that does not
exist» — آن هم ۵ بود و باید ۴ می‌بود. پیام کامیت تاریخ است و بازنویسی‌اش
نکردم؛ تصحیح در همین گزارش و در `REGRESSION_TEST_REPORT.md` ثبت شد.

## ۸. Critical Risks

### R1 — نبودِ بکاپ آزموده‌شده
**اثر:** از دست رفتن کل دادهٔ مشتری. **احتمال:** در هر استقرار واقعی، بالا.
**شواهد:** صفر کد؛ چرخهٔ دستیِ این ممیزی کار کرد ولی خودکار و تکرارپذیر نیست.
**رفع:** پیاده‌سازی `vira:backup` / `vira:restore` با مانیفست SHA-256 (طرح بخش ۳).

### R2 — نبودِ `composer.lock`
**اثر:** استقرار با نسخهٔ متفاوتِ وابستگی؛ خطایی که در آزمون دیده نشده.
**شواهد:** `git ls-files composer.lock` → خالی. علت: Packagist در محیط توسعه در
دسترس نبود.
**رفع:** یک بار `composer update` روی ماشینی با دسترسی شبکه، سپس commit.

### R3 — `VIRA_CREDENTIAL_KEY` هیچ سازوکار چرخشی ندارد
**اثر:** لو رفتن کلید = لو رفتن همهٔ رمزها، و چرخش کلید یعنی رمزنگاری مجدد همهٔ
`credential_values` که سازوکارش نوشته نشده.
**شواهد:** `EnvelopeEncrypter` پیشوند `v1:` دارد که برای نسخه‌بندی آماده است، ولی
هیچ ابزار migration کلید نیست.
**رفع:** فرمان چرخش کلید + نگه‌داری `v1:`/`v2:` همزمان در دورهٔ گذار.

### R4 — CBC در طرح بکاپ پیشنهادی اولیه
**اثر:** بکاپ دست‌کاری‌شده قابل تشخیص نبود.
**شواهد:** ثابت شد openssl روی فایل دست‌کاری‌شده exit 0 می‌دهد.
**وضعیت:** در معماری پیشنهادی به **GCM + مانیفست SHA-256** تغییر کرد. هنوز کد
نشده.

### R5 — تست روی SQLite، استقرار روی MariaDB
**اثر:** `UNSIGNED` در MySQL معنا دارد و در SQLite نه؛ `payroll_items.amount`
علامت‌دار نیست، پس روی MariaDB عدد منفی خطای out-of-range می‌دهد.
**شواهد:** `docs/DATABASE_SCHEMA.md` بند ۴.
**رفع:** اجرای سوئیت روی MariaDB پیش از انتشار.

## ۱۰. آنچه منتظر تأیید شماست

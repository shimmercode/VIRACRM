# معماری حسابداری — دفتر دوطرفه

## قواعد غیرقابل‌عبور (در کد اجرا می‌شوند، نه در سند)

| قاعده | کجا اجرا می‌شود |
|---|---|
| هر سند حداقل دو خط | `LedgerService::validateLines` |
| جمع بدهکار = جمع بستانکار | همان |
| هر خط بدهکار XOR بستانکار | همان |
| حساب گروهی قابل ثبت نیست | همان |
| مبلغ صفر مجاز نیست | همان |
| دوره بسته سند نمی‌پذیرد | `LedgerService::resolveOpenPeriod` |
| یک منبع = یک سند | `assertSourceNotAlreadyPosted` + ایندکس یکتای دیتابیس |
| سند قطعی ویرایش/حذف نمی‌شود | رویدادهای `updating`/`deleting` مدل |

## چرا `LedgerService` تنها مسیر نوشتن است

دوطرفه‌بودن یک مجموعه invariant است، نه یک ویژگی UI. اگر هر کنترلری بتواند مستقیم خط درج کند، دیر یا زود یکی سه خطِ نامتوازن وارد می‌کند و هر گزارش بالادست بی‌سروصدا غلط می‌شود. تمام نوشتن‌ها از این کلاس می‌گذرند.

## جدایی صدور فاکتور از دریافت وجه (بند ۱۹.۴)

صدور فاکتور:
```
Dr 1-1-02  حساب‌های دریافتنی     total
Cr 4-1-0x  درآمد                 subtotal − discount
Cr 2-1-02  مالیات فروش            tax_amount
```

دریافت وجه:
```
Dr 1-1-01  بانک و صندوق          amount
Cr 1-1-02  حساب‌های دریافتنی     amount
```

این دو، دو سند در دو زمان مختلف‌اند. مدیر اگر بپرسد «چقدر درآمد داشتیم» و اگر بپرسد «چقدر پول گرفتیم»، تا وقتی مشتری پرداخت نکرده باید دو جواب متفاوت بگیرد. تنها ساختاری که این را *به‌طور ساختاری* تضمین می‌کند همین است.

## مالکیت دوره و سود انباشته

ترازنامه در هر تاریخ داخل سال باز باید تراز باشد. درآمد و هزینه حساب ترازنامه‌ای نیستند، پس خالص آن‌ها به‌عنوان «سود/زیان دورهٔ جاری» به حقوق مالکانه اضافه می‌شود (`balanceSheet()` فیلد `net_profit`). بدون این انتقال، فاکتور دارایی را بالا می‌برد و حقوق مالکانه تا پایان سال صفر می‌ماند — یک دفترِ درست، ترازنامهٔ «نامتوازن» تولید می‌کند.

> این باگ در آزمون واقعی کشف شد (T-ACC-18) و سپس با تست `balanceSheetRollsProfitIntoEquity` تثبیت شد.

## «در دسترس نیست» ≠ صفر

`profitAndLoss()` وقتی هیچ سندی نیست `net = null` و `has_data = false` برمی‌گرداند. UI می‌نویسد «داده‌ای ثبت نشده است». نمایش «۰ ریال» به مدیر دروغ می‌گوید.

## ابعاد تحلیلی (بند ۱۹.۳)

هر خط سند می‌تواند `customer_id`, `contract_id`, `project_id`, `employee_id`, `department_id`, `cost_center_id`, `service_type` داشته باشد. برای هر مشتری حساب جدا ساخته نمی‌شود؛ سودآوری یک `GROUP BY` روی همین ستون‌هاست.

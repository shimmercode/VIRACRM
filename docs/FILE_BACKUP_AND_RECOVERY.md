# FILE_BACKUP_AND_RECOVERY — بکاپ و بازیابی Vira Drive

**نسخه:** 1.0 · **تاریخ:** ۲ آذر ۱۴۰۵ (2026-11-23) · **فاز:** F0 · **وضعیت:** Proposed — **هیچ کد بکاپی وجود ندارد**

> **وضعیت پایه (از فاز ۳):** CRM **صفر خط کد بکاپ** دارد. `BACKUP_RECOVERY.md` موجود طرح است، نه پیاده‌سازی.
> این سند برای Vira Drive **الزام** می‌سازد: بکاپی که بازیابی‌اش آزموده نشده، بکاپ نیست.

---

## ۱. دو داراییِ جدا که باید با هم بازیابی شوند

| دارایی | حجم (سناریو پایه سال ۱) | فرکانس تغییر | هزینهٔ از دست رفتن |
|--------|--------------------------|---------------|---------------------|
| **متادیتا** (MySQL: `file_*`) | ~۱.۳ GB | هر ثانیه | فاجعه — همه چیز بی‌نام می‌شود |
| **بایت‌ها** (Object Storage) | ~۶۵۰ GB | هر ثانیه | فاجعه — فایل‌ها گم می‌شوند |
| تنظیمات (`.env`, config) | <۱ MB | نادر | بازیابی سخت |
| Audit | در متادیتا | هر ثانیه | بی‌سابقه‌شدن |

**اصل:** بکاپ **ناهمگام** این دو، بی‌ارزش است. اگر متادیتای ساعت ۰۲:۰۰ با بایت‌های ۰۲:۳۰ بازیابی شود، بین‌شان ۳۰ دقیقه تناقض است.

## ۲. استراتژی — سه لایه

| لایه | چیست | RPO | RTO |
|------|------|:---:|:---:|
| **L1 — لحظه‌ای** | Snapshot VPS + MySQL binlog (اگر ممکن) | دقیقه | دقیقه |
| **L2 — روزانه** | Dump متادیتا + manifest بایت‌ها + همگام‌سازی افزایشی | ۲۴ ساعت | ساعت |
| **L3 — هفتگی** | نسخهٔ کامل آفلاین (کپی خارج از سایت) | هفته | روز |

### ۲.۱. RPO/RTO هدف

| سناریو | RPO قابل قبول | RTO قابل قبول | چرا |
|--------|:-------------:|:-------------:|-----|
| خطای اپراتور (حذف فایل) | ۰ | ۰ | Trash کافی است |
| خرابی DB | ۲۴h | ۴h | dump روزانه |
| خرابی VPS | ۲۴h | ۸h | snapshot + rebuild |
| خرابی Storage | ۲۴h | ۲۴h | replication |
| فاجعه (سایت) | ۱ هفته | ۷۲h | L3 |

**این اعداد پیشنهاد است و باید تأیید شود (OD-131).**

## ۳. بکاپ متادیتا

```bash
#!/usr/bin/env bash
# /usr/local/bin/vira-db-backup.sh
set -euo pipefail
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
OUT=/backup/db/vira-$STAMP.sql.gz
mysqldump --single-transaction --quick --routines --triggers \
          --default-character-set=utf8mb4 \
          "$DB_NAME" | gzip -9 > "$OUT"

# checksum برای تأیید صحت
sha256sum "$OUT" > "$OUT.sha256"

# رمزنگاری
age -r "$BACKUP_PUBKEY" -o "$OUT.age" "$OUT"
shred -u "$OUT"          # حذف نسخهٔ بدون رمز

# آپلود خارج از سایت
rclone copy "$OUT.age" remote:vira-backup/db/
```

| نکته | چرا |
|------|-----|
| `--single-transaction` | بدون قفل جدول |
| رمزنگاری **قبل** از آپلود | بکاپ در فضای ابری بدون رمز = افشا |
| `shred` نسخهٔ موقت | جلوگیری از باقی‌ماندن |
| checksum | تشخیص خرابی |

## ۴. بکاپ بایت‌ها

### ۴.۱. اگر Storage = Object Storage

| روش | مزیت | عیب |
|------|------|-----|
| **Versioning روی bucket** | ساده، پوشش حذف | هزینهٔ نگهداری |
| **Replication به bucket دوم** | جداسازی | هزینهٔ دوبرابر |
| **rsync به دیسک محلی** | ارزان | کند |

**پیشنهاد:** Versioning + Replication به منطقه/سرویس دوم. **OD-132.**

### ۴.۲. اگر Storage = دیسک VPS

```bash
# روزانه، افزایشی
rsync -aHAX --delete --link-dest=/backup/files/current \
      /srv/vira-files/ /backup/files/$STAMP/
ln -sfn /backup/files/$STAMP /backup/files/current
```

| نکته | چرا |
|------|-----|
| `--link-dest` | hardlink، صرفه‌جویی فضا |
| **قبل از هر بکاپ، یک manifest بساز** | تا بدانی چه باید باشد |

### ۴.۳. Manifest — قطعهٔ کلیدی

```php
// قبل از بکاپ
$rows = DB::table('file_blobs')
    ->select('sha256', 'size_bytes', 'storage_key', 'storage_location_id')
    ->get();

Storage::disk('backup')->put("manifests/$stamp.json", json_encode($rows));
```

**چرا:** بعد از بازیابی، می‌توانی بپرسی «آیا هر blob در manifest، واقعاً موجود است و هش‌اش درست است؟». بدون manifest، بازیابی یک «امید» است.

## ۵. بازیابی — ترتیب اجباری

```
1) متادیتا را بازیابی کن (DB dump)
2) manifest را بخوان
3) برای هر blob: آیا فایل موجود است؟
      خیر → از بکاپ بازیابی کن
4) برای نمونه‌ای (۱٪ یا ۵۰۰ رکورد): هش را بازمحاسبه کن
      ناهمخوان → علامت‌گذاری + گزارش
5) رابطهٔ نسخه↔blob را بررسی کن
      نسخه‌ای که blob ندارد → علامت‌گذاری به‌عنوان corrupted
6) مجوزها را بازبینی کن (تعداد + نمونه)
7) WebDAV را وصل و smoke test
8) گزارش نهایی
```

### ۵.۱. اسکریپت بررسی یکپارچگی (طرح)

```php
final class IntegrityCheck
{
    public function run(int $samplePercent = 1): IntegrityReport
    {
        $missing = [];
        $mismatched = [];

        DB::table('file_versions')
            ->join('file_blobs', 'file_blobs.id', '=', 'file_versions.blob_id')
            ->whereNull('file_versions.purged_at')
            ->orderByRaw('RAND()')
            ->limit($this->sampleCount($samplePercent))
            ->get()
            ->each(function ($r) use (&$missing, &$mismatched) {
                if (! Storage::disk($r->disk)->exists($r->storage_key)) {
                    $missing[] = $r->sha256;
                    return;
                }
                $actual = hash_file('sha256', Storage::disk($r->disk)->path($r->storage_key));
                if (! hash_equals($r->sha256, $actual)) {
                    $mismatched[] = $r->sha256;
                }
            });

        return new IntegrityReport($missing, $mismatched);
    }
}
```

**نکته:** `hash_file` روی فایل ۱GB حافظه نمی‌خورد (استریم داخلی)، ولی CPU می‌برد. برای همین **نمونه‌گیری**، نه همه.

## ۶. آزمون بازیابی (الزامی، نه اختیاری)

| # | آزمون | فرکانس | معیار |
|---|-------|--------|-------|
| R1 | بازیابی DB به schema خالی | فصلی | row count منطبق |
| R2 | بازیابی ۱۰۰ blob تصادفی | فصلی | هش منطبق |
| R3 | بازیابی کامل به محیط جدا | نیم‌ساله | اپ بالا بیاید |
| R4 | بررسی رابطهٔ نسخه↔blob | هر بازیابی | ۰ یتیم |
| R5 | ثبات مجوز | هر بازیابی | نمونه درست |
| R6 | WebDAV پس از بازیابی | هر بازیابی | mount شود |
| R7 | اندازه‌گیری RTO | هر بازیابی | مستند |
| R8 | آزمون فاجعه (بدون هیچ بکاپ محلی) | سالانه | فقط از L3 |

**قاعدهٔ سخت:** تا R1–R6 حداقل یک بار اجرا نشوند، سیستم **«بکاپ‌دار»** اعلام نمی‌شود.

## ۷. حفاظت از خود بکاپ

| تهدید | کنترل |
|-------|-------|
| بکاپ عمومی | هرگز در `public/`، هرگز bucket عمومی |
| بکاپ بدون رمز | `age`/`gpg` اجباری |
| Ransomware | L3 آفلاین / WORM |
| حذف اشتباه | نگهداری چند نسخه، `--link-dest` |
| دسترسی داخلی | فقط ادمین + Audit روی دانلود بکاپ |
| کلید گم‌شده | دو کپی از `BACKUP_PUBKEY`/private key در مکان جدا (OD-29 مرتبط) |

**نکتهٔ OD-29:** کارفرما ریسک گم‌شدن کلید را پذیرفته، ولی «مدیریت امن کلید + بکاپ/بازیابی» **الزام** است. برای بکاپ، این یعنی: کلید خصوصی رمزگشایی باید در **حداقل دو** مکان امن و مستقل باشد.

## ۸. سناریوهای بازیابی مشخص

| # | سناریو | اقدام | RTO |
|---|--------|-------|-----|
| S1 | کاربر فایلی را حذف کرد | Trash → Restore | ثانیه |
| S2 | فایل به‌طور کامل پاک شد (hard delete) | از بکاپ روز قبل + manifest | ساعت |
| S3 | نسخهٔ اشتباه بازگردانی شد | Restore نسخهٔ درست (نسخهٔ جدید) | ثانیه |
| S4 | جدول `file_versions` خراب شد | بازیابی DB + بررسی یتیم | ۲–۴ ساعت |
| S5 | Object Storage از دسترس خارج شد | failover به replica | دقیقه–ساعت |
| S6 | VPS سوخت | rebuild از snapshot + بازیابی storage | ۴–۸ ساعت |
| S7 | فاجعهٔ سایت | L3 | ۲۴–۷۲ ساعت |
| S8 | فایل corrupted (هش ناهمخوان) | از بکاپ نسخهٔ سالم؛ اگر نبود → علامت corrupted | متغیر |

# CRM_REVIEW_MODEL_A — سه شکاف مدل، بدون تغییر Migration

> این سند **طراحی** است. هیچ Migration، هیچ Schema و هیچ جدولی ساخته نشده.
> §21 صریحاً می‌گوید در این فاز Migration سازمانی ممنوع است.
>
> اما طراحی بدون اجرا، وظیفه است — و طراحی بدون سناریو، ادعاست.

## بخش ۶ — غیرفعال‌سازی کارمند و قاعدهٔ «دسترسی مؤثر»

### ۶.۱ شکاف

| واقعیت امروز | پیامد |
|---|---|
| `users.is_active` یک پرچم است | ورود را کنترل می‌کند |
| `employees.status` یک رشتهٔ متنی است (`active`/`inactive`/`terminated`) | ورود را کنترل **نمی‌کند** |
| هیچ کدی این دو را هم‌گام نمی‌کند | کارمند پایان‌همکاری‌گرفته می‌تواند حساب فعال داشته باشد |
| `employees.user_id` قابل NULL است | کاربر بدون رکورد کارمند وجود دارد |
| `employees.deleted_at` (SoftDeletes) | حذف نرم، دسترسی را قطع نمی‌کند |

**بازرسی ماشینی همین حالا:** در محیط بازبینی، کارمند `RVW-E-0007` وضعیت
`inactive` دارد و هیچ کاربر سامانه ندارد؛ `RVW-E-0008` وضعیت `terminated`
دارد. هیچ‌کدام حساب فعال ندارند — اما این **تصادف داده** است، نه قاعدهٔ کد.

### ۶.۲ نُه سناریو (اجباری)

| # | سناریو | وضعیت امروز | حکم لازم در Model A |
|:-:|---|---|---|
| S1 | کارمند فعال + کاربر فعال | کار می‌کند | ✅ دسترسی کامل |
| S2 | کارمند `inactive` + کاربر فعال | **شکاف** — دسترسی ادامه دارد | ❌ باید قطع شود |
| S3 | کارمند `terminated` + کاربر فعال | **شکاف** — دسترسی ادامه دارد | ❌ باید قطع شود فوری |
| S4 | کارمند فعال + کاربر `is_active=0` | ورود قطع است | ❌ ورود ممنوع؛ ولی رکورد کارمند برای حقوق باقی می‌ماند |
| S5 | کارمند فعال، بدون رکورد کاربر | نمی‌تواند وارد شود | ⚠️ تعریف: کارمند بدون کاربر = شخص حقوقی، بدون دسترسی سامانه |
| S6 | کاربر فعال، بدون رکورد کارمند | ورود ممکن است | ⚠️ تعریف: کاربر «سیستمی» — فقط نقش، بدون حقوق/تخصیص پروژه |
| S7 | **نشست زنده** هنگام غیرفعال‌سازی | بسته نمی‌شود | ❌ باید در همان درخواست بعدی رد شود |
| S8 | **توکن WebDAV زنده** هنگام غیرفعال‌سازی | وجود ندارد | ❌ باید باطل شود؛ پیش‌فرض Fail-Closed |
| S9 | **اشتراک/قفل فایل (Share/Lock)** هنگام غیرفعال‌سازی | وجود ندارد | ❌ اشتراک باید لغو، قفل باید آزاد شود، با audit |

### ۶.۳ قواعد پیشنهادی (طراحی، نه اجرا)

```
دسترسی مؤثر = min(users.is_active, employees.status)   // هر کدام «خیر» ⇒ «خیر»
```

**قاعدهٔ قطعی (Fail-Closed):** اگر رکورد کارمند وجود داشته باشد و وضعیتش
`inactive` یا `terminated` باشد، **دسترسی سامانه صفر است** — صرف‌نظر از
`users.is_active`.

### ۶.۴ چهار پرسش باز که این سند **پاسخ نمی‌دهد**

| پرسش | چرا باز است |
|---|---|
| **مرجع نهایی احراز هویت کیست؟** | `users` یا `employees`؟ پاسخ به این بستگی دارد که آیا شخص می‌تواند بدون رکورد کارمند وارد شود (S6) |
| **ابطال نشست چطور انجام می‌شود؟** | Laravel session در پایگاه داده است؛ پاک‌کردن ردیف کاربر کافی نیست. **تست نشده** |
| **ابطال توکن WebDAV چطور؟** | ماژول وجود ندارد. طرح: شناسهٔ توکن در جدول، با `revoked_at` |
| **کش مجوز کجا و کِی باطل می‌شود؟** | OD-107 (TTL ۳۰ ثانیه) — یعنی تا ۳۰ ثانیه پنجرهٔ نشت وجود دارد |

### ۶.۵ رفتار کاربران بدون رکورد کارمند

| حالت | پیشنهاد |
|---|---|
| S5 (کارمند بدون کاربر) | رکورد حقوقی/عملیاتی است؛ **هیچ دسترسی سامانه ندارد**. در UI با برچسب «بدون دسترسی» نمایش داده شود |
| S6 (کاربر بدون کارمند) | کاربر «سیستمی» است (مثلاً حساب یکپارچه‌سازی). فقط نقش، بدون حقوق و بدون تخصیص پروژه. **باید در UI علامت‌گذاری شود** |

**تصمیم نهایی: باز (OD-119).** این سند سناریوها را تعریف می‌کند تا تصمیم
قابل گرفتن باشد؛ خودش تصمیم نمی‌گیرد.

## بخش ۷ — تفکیک دپارتمان / گروه / تیم پروژه / نقش

### ۷.۱ چهار مفهوم، چهار سؤال

| مفهوم | سؤال | منبع | امروز |
|---|---|---|---|
| **نقش (Role)** | چه کاری **مجاز** است؟ | `roles` + `role_permissions` | ✅ موجود (۴ نقش) |
| **دپارتمان (Department)** | در سازمان **کجاست**؟ | `departments` + `user_departments` | ❌ وجود ندارد |
| **گروه (Group)** | **دستی** چه کسانی کنار هم‌اند؟ | `file_groups` + `file_group_members` | ❌ وجود ندارد |
| **تیم پروژه (Project Team)** | روی **چه پروژه‌ای** کار می‌کند؟ | `project_assignments` | ✅ موجود (۱۵ ردیف ساختگی) |

### ۷.۲ تصمیم لازم دربارهٔ «تیم»

اگر «تیم» در محصول از `project_assignments` مشتق شود، سه پیامد قطعی دارد:

1. **نامش در UI باید «تیم پروژه» باشد** — نه «تیم». چون یک فرد می‌تواند در
   دو پروژهٔ دو دپارتمان مختلف باشد.
2. **مجوزهایش از پروژه می‌آید، نه از دپارتمان** — و این یعنی باید مشخص شود
   آیا عضویت پروژه می‌تواند محرمانگی دپارتمان را دور بزند (پاسخ پیشنهادی: **نه**).
3. **پایان عضویت (`is_active=0`) باید دسترسی را قطع کند** — امروز هیچ کدی
   این را نمی‌خواند.

**در محیط بازبینی:** صفحهٔ `/review/preview/project-team` این ۱۵ تخصیص واقعی را
نمایش می‌دهد و **همان‌جا** می‌نویسد که نمایش داده اثبات مجوز نیست.
**تصمیم: باز (OD-118، OD-120، OD-121).**

### ۷.۳ چرا جدول خالی اثبات نیست

`project_assignments` در دیتابیس توسعه **۰ ردیف** داشت. با ۰ ردیف، هر
صفحه‌ای «کار می‌کند» چون هیچ‌چیز برای شکستن نیست. بنابراین
`database/seeders/ReviewDemoSeeder.php` پانزده تخصیص ساختگی ساخت — از جمله:

- فردی در دو پروژه با دو دپارتمان مختلف
- عضوی از خارج دپارتمان پروژه
- یک عضویت پایان‌یافته (`ended_on` پر، `is_active=0`)

این داده‌ها **شکاف را نشان می‌دهند**؛ نمی‌بندند.

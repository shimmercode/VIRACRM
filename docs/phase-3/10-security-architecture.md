# 10 — معماری امنیت (Gate A)

**Vira CRM** · Gate A · ۲ آذر ۱۴۰۵

CRM شامل **رمزهای وردپرس مشتریان**، **اطلاعات هویتی** و **حقوق کارمندان** است.
این یعنی سطح حساسیت آن از یک پنل معمولی بالاتر است.

---

## ۱. طبقه‌بندی داده (چهار سطح)

| سطح | داده | ذخیره | دسترسی | نگهداری |
|-----|------|-------|--------|---------|
| **۱ — عادی** | نام مشتری، دامنه، وضعیت پروژه | plaintext | همهٔ نقش‌های مجاز | تا حذف رکورد |
| **۲ — شخصی** | کد ملی، موبایل، آدرس، ایمیل | plaintext + `search_key` | مجوز ماژول | `REQ-15` — **مدت نگهداری تصمیم نشده (OD-28)** |
| **۳ — مالی** | مبالغ قرارداد، حقوق، فیش | `integer` ریال | `*_view_financials` + `payroll.*` (sensitive) | تاریخچهٔ دائمی |
| **۴ — فوق‌محرمانه** | رمز وردپرس/هاست/ثبت‌دامنه | **AES-256-GCM envelope** | `credentials.reveal` (sensitive) + re-auth | تا حذف/invalidate |

## ۳. رمزنگاری — مکانیزم، کلید، چرخش، بازیابی

### مکانیزم (موجود و تست‌شده)

`EnvelopeEncrypter` — **AES-256-GCM** با `openssl_encrypt`، هر مقدار:
`nonce` تصادفی + `tag` + `ciphertext`، همه base64. ۲۶ اَسِرشِن قبول.

**این طراحی درست است و تغییر نمی‌کند.** الگوریتم اختصاصی ساخته نشده.

### منبع کلید

| گزینه | ارزیابی |
|-------|---------|
| `APP_KEY` موجود | ⚠️ خطرناک — چرخش `APP_KEY` همهٔ رمزها را از بین می‌برد |
| **کلید جدا `VIRA_CREDENTIAL_KEY`** | ✅ **پیشنهاد** — چرخش مستقل از نشست‌ها |
| KMS خارجی | ❌ هاست اشتراکی، در دسترس نیست |

**پیشنهاد:** کلید ۳۲ بایتی جداگانه در `.env` (مجوز ۶۰۰، خارج از Git)، تولید با
`EnvelopeEncrypter::generateKey()`.

### چرخش کلید (key rotation)

طرح دو کلید:

```
VIRA_CREDENTIAL_KEY       ← کلید فعال (رمزگذاری جدید)
VIRA_CREDENTIAL_KEY_OLD   ← کلید قبلی (فقط رمزگشایی)
```

فرمان `vira:credentials:rotate-key`:
۱. همهٔ رکوردها را با کلید فعال رمزگشا و با کلید جدید رمزگذاری می‌کند.
۲. هر رکورد در تراکنش خودش.
۳. اگر رکوردی رمزگشا نشد → **توقف کامل** و گزارش (نه نادیده‌گرفتن).
۴. پس از موفقیت، `_OLD` حذف می‌شود.

### پیامد بکاپ (حیاتی)

> **بکاپ DB بدون کلید رمزنگاری، رمزهای دسترسی را بازیابی‌ناپذیر می‌کند.**

این باید در سند بکاپ و runbook صریح نوشته شود. **همهٔ بکاپ‌ها باید رمزگذاری شوند** و
کلید **جدا از بکاپ** نگهداری شود (یا در گاوصندوق/مدیر رمز).

### بازیابی

| سناریو | نتیجه |
|--------|-------|
| کلید گم شود | **رمزها بازگشت‌ناپذیرند.** دسترسی‌ها باید دستی بازنویسی شوند |
| بکاپ بدون کلید | همان |
| کلید لو برود | همهٔ رمزها را باید عوض کرد + چرخش کلید |

**این ریسک باید کتباً به شما اعلام شود (OD-29).**

## ۴. `CredentialVault` — قواعد سخت

| قاعده | جزئیات |
|-------|--------|
| فهرست هرگز رمز ندارد | کوئری فهرست فقط `id, type, label, username, updated_at, fingerprint` |
| Reveal با `POST` | نه `GET` — تا در history مرورگر و log پروکسی ننشیند |
| `Cache-Control: no-store` | روی پاسخ reveal |
| هر reveal → Audit | `credential.reveal` با `user_id, credential_id, ip, at` — **بدون مقدار** |
| خودکار مخفی پس از ۳۰s | در UI |
| Re-auth برای reveal | اگر نشست >۱۵ دقیقه، رمز دوباره خواسته شود (**OD-26**) |
| Export PDF محرمانه | مجوز جدا `credentials.export` + Audit + هشدار محرمانگی روی سند |
| بدون رمز در URL | هرگز `?password=` |
| بدون رمز در JS console | داده فقط با کلیک واکشی می‌شود، نه از متغیر global |

## ۵. مجوزها — سه لایه، بدون استثنا

```
لایه ۱: سایدبار      → آیتم بدون مجوز پنهان (UX فقط)
لایه ۲: middleware   → permission:xxx (امنیت واقعی)   ✅ امروز روی ۲۰ مسیر
لایه ۳: Policy       → رکورد مشخص (امنیت واقعی)      ⚠️ باید اضافه شود
```

**شکاف فعلی:** هیچ `app/Policies/` وجود ندارد. `permission:` می‌گوید «می‌توانی
قرارداد ببینی»، ولی نمی‌گوید «این قرارداد خاص». برای دامنهٔ تک‌مدیره امروز کافی
است؛ برای نقش «کارشناس حساب» **کافی نیست**.

**برنامه:** Policy برای `Contract`, `Project`, `Credential`, `Payslip` اضافه می‌شود.

## ۷. امنیت PDF — چالش واقعی

PDF می‌تواند **بیشترین نشتی** را ایجاد کند، چون فایل دانلود می‌شود و از کنترل
سرور خارج است.

| قاعده | پیاده‌سازی |
|-------|-----------|
| PDF عمومی پروژه **هرگز** رمز ندارد | تست خودکار: محتوای PDF عمومی را باز کن و مطمئن شو هیچ `value_ciphertext` رمزگشایی‌شده‌ای در آن نیست |
| PDF محرمانه درخواست مجوز جدا | `credentials.export` |
| فایل تولیدشده در `storage/app/private/pdf/` | خارج از public |
| دانلود با Route محافظت‌شده، بدون URL دائمی | `Response::download` با `permission:` |
| هشدار محرمانگی روی هر صفحه | واترمارک «محرمانه» + نام دریافت‌کننده + تاریخ |
| ثبت هر export | Audit |
| رمزگذاری PDF (اختیاری) | اگر موتور PDF پشتیبانی کند (**OD-31**) |

## ۱۰. جمع‌بندی صادقانه

**قوی:** ورود، مجوزها، رمزنگاری، Audit، CSRF/XSS/SQLi — همه طراحی درست دارند.

**ضعیف:** Policy (لایهٔ سوم) نیست، ماژول دسترسی‌ها وجود ندارد، امنیت PDF
پیاده نشده، تست امنیتی برای IDOR وجود ندارد چون سطح حمله (آپلود/دسترسی) هنوز ساخته نشده.

**پس «امن امروز» یعنی: سیستم کوچکی که هنوز دادهٔ حساس ندارد، امن است.** این با
«امنیت کامل» یکی نیست، و نباید یکی شمرده شود.

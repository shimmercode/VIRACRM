در بسته اولیه فاز ۱ نوشته بودیم: «morilog نوروز ۱۴۰۴ را ۲۰۲۵-۰۳-۲۰ می‌گذارد».
**این اشتباه بود.** منشأ اشتباه، یک اسکریپت آزمایشی خودمان بود
(`docs/src/jalali-smoke-test.php`) که الگوریتم **حسابی ۲۸۲۰ ساله** را پیاده کرده بود،
نه morilog را. آن اسکریپت ۲۰۲۵-۰۳-۲۰ می‌داد و ما آن را به morilog نسبت دادیم.

**واقعیت (با سه مرجع مستقل تأیید شد):**

## ۳. لایه‌بندی فنی (چرا تبدیل تاریخ همه‌جا پخش نمی‌شود)

```
┌──────────────────────────────────────────────────────────┐
│ 1. لایه ذخیره‌سازی: MySQL DATE/DATETIME (میلادی)        │
│    هیچ تاریخ شمسی در DB ذخیره نمی‌شود                     │
└──────────────────────────────────────────────────────────┘
                      ▲              │
                      │              ▼
┌──────────────────────────────────────────────────────────┐
│ 2. لایه دامنه: Carbon + Asia/Tehran                       │
│    منطق یادآور، مقایسه تاریخ‌ها، محاسبات همه اینجا         │
└──────────────────────────────────────────────────────────┘
                      ▲              │
                      │              ▼
┌──────────────────────────────────────────────────────────┐
│ 3. لایه نمایش: JalaliPresenter (تنها نقطه تبدیل)          │
│    Blade Component + API Resource                        │
└──────────────────────────────────────────────────────────┘
```

**قاعده:** هیچ FormRequest، Service یا Query مستقیم تاریخ شمسی نمی‌سازد.
همه ورودی‌های شمسی از یک مسیر (`JalaliInput`) به تاریخ میلادی تبدیل می‌شوند و همه
خروجی‌ها از یک مسیر (`JalaliPresenter`) به شمسی. اگر این قاعده شکسته شود،
یک باگ تاریخ در ده جای مختلف ظاهر می‌شود.

## ۶. الگوریتم ۲۸۲۰ — چرا حذف می‌شود

### ۶.۱ مشکل چیست؟

تقویم حسابی ۲۸۲۰ ساله یک چرخه ریاضی با ۶۸۳ سال کبیسه در ۲۸۲۰ سال است. این تقویم
**تقویم نجومی رسمی ایران نیست**. ایران از ۱۳۰۴ شمسی تقویم نجومی دارد: نوروز روزی است
که اعتدال بهاری پیش از ظهر تهران رخ دهد، وگرنه روز بعد.

### ۶.۲ این چه اثری دارد؟

| سال | نوروز درست | الگوریتم ۲۸۲۰ | اختلاف |
|---|---|---|---|
| ۱۴۰۳ | ۲۰۲۴-۰۳-۲۰ (کبیسه، اسفند ۳۰) | ۲۰۲۴-۰۳-۲۰ ✓ ولی **عادی** ❌ | طول سال غلط |
| **۱۴۰۴** | **۲۰۲۵-۰۳-۲۱ (عادی)** | **۲۰۲۵-۰۳-۲۰ (کبیسه)** ❌ | **۱ روز** |
| ۱۴۳۷ | ۲۰۵۸-۰۳-۲۱ | ۲۰۵۸-۰۳-۲۰ ❌ | ۱ روز |

در بازه ۱۳۵۰–۱۴۶۰ فقط **دو** سال اختلاف دارند: **۱۴۰۴** و **۱۴۳۷**.
ولی همین دو مورد کافی است: یک فاکتور با تاریخ ۲۹ اسفند ۱۴۰۴ یا یک گزارش سئو در
نوروز ۱۴۰۴ در سیستم غلط ثبت می‌شود و **خطا در سطح داده است، نه نمایش** — یعنی
بعداً قابل جبران نیست.

### ۶.۳ تصمیم

| اقدام | وضعیت |
|---|---|
| حذف `docs/src/jalali-smoke-test.php` (موتور ۲۸۲۰) از مسیر محصول | تصمیم گرفته شد |
| جایگزینی با verifier مبتنی بر الگوریتم morilog | انجام شد (`docs/src/jalali-golden-verify.php`) |
| ثبت این تصحیح در ADR به‌عنوان addendum | انجام شد (`01-architecture-decision-record.md`) |
| هیچ کد محصولی از الگوریتم ۲۸۲۰ استفاده نمی‌کند | تضمین با بازبینی کد در فاز ۲ |

> **نکته صداقتی:** ما نمی‌گوییم «۲۸۲۰ همیشه غلط است». در بسیاری از سال‌ها با تقویم
> نجومی یکسان است. می‌گوییم «برای ۱۴۰۴ و ۱۴۳۷ غلط است و برای یک CRM مالی این
> کافی است که کنار گذاشته شود».

## ۷. محاسبه D-2 — مستقل از تصمیم تقویم

مهم‌ترین ویژگی طراحی: **یادآور D-2 به هیچ الگوریتم شمسی وابسته نیست.**

```
due_date   DATE میلادی  (مثلاً 2026-03-21)
fire_date  = due_date − 2 روز تقویمی  (2026-03-19)
اجرا       فقط اگر «روز تقویمی تهران» لحظه اجرا == fire_date
```

چون `due_date` از نوع `DATE` است و ساعت ندارد، ساعت اجرای job هیچ اثری بر روز ندارد.
این **دو روز تقویمی** است، نه «۴۸ ساعت شناور».

**اثبات اجراشده** (`evidence/d2-daymath-verify.json`، ۲۲ بررسی، PHP ۸.۲ و ۸.۳ PASS):

| بررسی | نتیجه |
|---|---|
| D-2 در مرز نوروز (۱۴۰۵ و ۱۴۰۴) | PASS |
| D-2 در مرز سال میلادی و ماه | PASS |
| D-2 با ۲۹ فوریه (۲۰۲۸) در مسیر | PASS |
| ساعت ۰۰:۰۵ و ۲۳:۵۹ روز موعد هر دو اجرا می‌شوند | PASS |
| روز قبل هرگز اجرا نمی‌شود | PASS |
| ۲۱:۰۰ UTC = ۰۰:۳۰ تهران روز بعد | PASS |
| آفست ثابت +۰۳:۳۰ در تمام سال | PASS |
| `unique_key` پایدار و یکتا (۶۴ کاراکتر sha256) | PASS |
| تغییر تاریخ موعد → کلید جدید (یادآور قدیمی برنمی‌گردد) | PASS |
| کد محاسبه D-2 هیچ فراخوانی تبدیل شمسی ندارد | PASS |

> **عاقبت طراحی:** اگر کارفرما فردا تصمیم بگیرد تقویم دیگری استفاده شود، منطق یادآور

> Q-06 بدون مسدود کردن توسعه باز بماند.

# معماری Backup و Restore

**وضعیت:** طراحی نهایی‌شده؛ پیاده‌سازی در همین چرخه.
**جایگزین:** طرح AES-256-CBC در `BACKUP_RESTORE_GUIDE.md` — آن طرح **لغو شد**.

> هر قابلیتی که این سند به آن تکیه می‌کند، در همین محیط سنجیده شده است
> (`tools/checks/env-capabilities.php`). هیچ مسیری فرض نشده.

---

## ۰. آنچه از محیط واقعی تأیید شد

| قابلیت | نتیجه | چگونه |
|---|---|---|
| `aes-256-gcm` | **موجود** و اصالت‌سنجی می‌کند | رمزگشایی با ciphertext/tag/کلید دست‌کاری‌شده → `false` |
| OpenSSL | 1.1.1t | `OPENSSL_VERSION_TEXT` |
| `hash_hkdf` | موجود | خروجی ۳۲ بایت |
| `hash_hmac` / `hash_equals` | موجود | — |
| `random_bytes` | موجود | — |
| `SQLite3::backup()` | **موجود و کارکردی** | ۸۴۷٬۸۷۲ بایت، `integrity_check: ok` |
| `VACUUM INTO` | موجود (SQLite 3.51.0) | جایگزین تأییدشده |
| `ZipArchive` | موجود | — |
| `PDO` | `mysql,sqlite` | — |
| `storage/` writable | بله | `is_writable()` |
| `storage/` در وب | **خیر** | `public/` فقط `build`, `favicon.ico`, `index.php`, `robots.txt` |
| `memory_limit` | **256M** | محدودیت واقعی طراحی |
| `exec()` | در این محیط callable — **روی هاست ممکن است غیرفعال باشد** | `disable_functions` |

**نتیجهٔ طراحی:** هیچ مسیری به `exec`، `tar`، `sqlite3` CLI یا shell ندارد. همه
با PHP خالص انجام می‌شود.

## ۱. چرا CBC لغو شد و GCM انتخاب شد

`BACKUP_RESTORE_GUIDE.md` طرح AES-256-CBC داشت. ممیزی ثابت کرد CBC اصالت‌سنجی
ندارد: فایل دست‌کاری‌شده با `exit 0` رمزگشایی شد.

GCM در همین محیط آزموده شد و هر سه حالت را رد کرد:

| دست‌کاری | نتیجه |
|---|---|
| ciphertext | `false` |
| tag | `false` |
| کلید | `false` |

**پس به Encrypt-then-MAC نیازی نیست.** آن راهکار فقط در صورت نبودِ GCM لازم
می‌شد؛ چون GCM هست، افزودن HMAC جدا یعنی دو مکانیزم اصالت‌سنجی که باید هر دو
درست بمانند. اگر روزی روی هاستی GCM نبود، `BackupCipher` با
`hash_hmac('sha256', …)` + `hash_equals` روی `header ‖ ciphertext` به
Encrypt-then-MAC برمی‌گردد — همان قالب، فقط `cipher` در هدر عوض می‌شود.

## ۲. قالب کانتینر `.vbk1`

```
┌ magic   8 بایت   "VIRABK1\n"
├ header  یک خط JSON + "\n"
└ body    gzip(payload) رمزنگاری‌شده با AES-256-GCM
```

**header:**

```json
{
  "cipher": "aes-256-gcm",
  "kdf": "hkdf-sha256",
  "kdf_iterations": 1,
  "salt": "<base64, 16 بایت تصادفی>",
  "iv":   "<base64, 12 بایت تصادفی>",
  "tag":  "<base64, 16 بایت>",
  "manifest_sha256": "<64 hex>",
  "created_at": "2026-11-25T12:00:00+00:00",
  "payload_bytes": 12345,
  "app": { "php": "8.3.36", "sqlite": "3.51.0" }
}
```

**payload** یک ZIP است شامل:

| عضو | محتوا |
|---|---|
| `manifest.json` | فهرست فایل‌ها با SHA-256 و اندازهٔ هرکدام |
| `database.sqlite` | خروجی `SQLite3::backup()` |
| `files/…` | درخت `storage/app/private` و `storage/app/public` |

**چرا یک tag روی کل body:** هر دست‌کاری در هر بایتی از payload — دیتابیس، فایل‌ها
یا خودِ manifest — همان یک tag را می‌شکند. این ساده‌ترین طرحی است که «فایل
دست‌کاری‌شده» را قطعی رد می‌کند.

## ۳. حفاظت از کلیدها

| کلید | منبع |کاربرد |
|---|---|---|
| `VIRA_CREDENTIAL_KEY` | `.env` | رمزنگاری `credential_values` |
| `VIRA_BACKUP_KEY` | `.env` | رمزنگاری فایل بکاپ |

**دو کلید مستقل، و این الزام مرحلهٔ ۱.۵ است.** دلیل:

- اگر یک کلید بودند، لو رفتن بکاپ = لو رفتن کلیدِ رمزنگاری رمزها.
- چرخش یکی نباید دیگری را باطل کند.
- بکاپ باید بتواند به فضای خارجی برود؛ کلیدش نباید همان کلیدی باشد که هرگز از
  سرور بیرون نمی‌رود.

**اشتقاق:** `hash_hkdf('sha256', VIRA_BACKUP_KEY, 32, 'vira-backup-v1', salt)`.
نمک تصادفی برای هر بکاپ، پس کلید مشتق‌شده برای هر فایل متفاوت است.

**قاعدهٔ ذخیره:** `VIRA_BACKUP_KEY` **هرگز** داخل فایل بکاپ نوشته نمی‌شود و
**هرگز** همراه بکاپ به فضای خارجی نمی‌رود. اگر برود، بکاپ دیگر محافظت‌شده نیست.

## ۴. محل ذخیره

`storage/app/backups/`

| بررسی | نتیجه |
|---|---|
| داخل `public/`؟ | **خیر** — `public/` فقط ۴ قلم دارد |
| gitignore؟ | بله — `storage/app/.gitignore` محتوا `*` است با استثنا برای `private/` و `public/` |
| writable؟ | بله (تأیید شد) |
| از وب قابل دانلود؟ | نه — هیچ route ای به آن اشاره نمی‌کند |

نام فایل: `vira-backup-YYYY-MM-DD-HHmmss.vbk1` + یک نسخهٔ `.sha256` کنارش.

## ۵. سیاست نگهداری

| دسته | تعداد نگه‌داشته |
|---|---|
| روزانه | ۷ |
| هفتگی | ۴ |
| ماهانه | ۶ |

حذف **فقط پس از موفقیت کامل بکاپ جدید** انجام می‌شود. اگر بکاپ جدید شکست بخورد،
هیچ فایل قدیمی‌ای حذف نمی‌شود — حذف نسخهٔ سالم به‌خاطر شکست نسخهٔ تازه، بدترین
زمان برای از دست دادن بکاپ است.

مقادیر از `config('vira.backup_retention')` خوانده می‌شوند و با
`VIRA_BACKUP_KEEP_DAILY` / `_WEEKLY` / `_MONTHLY` قابل تغییرند. روی فرمان فقط
`--no-prune` وجود دارد (هیچ چیز را حذف نکن). پرچم `--keep=N` در طراحی اولیه
ذکر شده بود ولی **پیاده‌سازی نشد** — سه متغیر محیطی روشن‌تر از یک پرچم هستند و
نیمه‌کاره رهایش نکردیم.

**معنی دقیق هر دسته:** در هر دورهٔ زمانی **فقط یک** کانتینر — تازه‌ترین —
نگه داشته می‌شود، و یک کانتینر اگر هر یک از دسته‌ها او را نگه دارد باقی می‌ماند.
این جمله بار امنیتی دارد، نه توضیحی: نخستین پیاده‌سازی «همهٔ فایل‌های N دورهٔ
آخر» را نگه می‌داشت، دسته‌ها کاملاً روی هم می‌افتادند، و در نتیجه pruning
**هرگز چیزی را حذف نمی‌کرد**. با ۲۱ کانتینر در ۲۰ روز، خروجی فرمان
`pruned : 0` بود. منطق انتخاب اکنون در `app/Services/Backup/RetentionPolicy.php`
است — تابعی خالص، بدون لاراول — و `BackupRestoreTest` آن را قفل می‌کند.

**اندازه‌گیری واقعی:** ۲۰ کانتینر روزانهٔ متوالی + ۱ بکاپ تازه با سیاست ۷/۴/۶
→ خروجی `pruned : 12`، باقی‌مانده ۹ (۷ روزانه + ۲ هفتگی)، بدون sidecar یتیم.

## ۶. رفتار در شکست

### شکست Backup

1. روی فایل موقت با پسوند `.partial` نوشته می‌شود.
2. فقط پس از موفقیت رمزنگاری و تأیید SHA-256، با `rename()` به نام نهایی
   منتقل می‌شود — `rename` روی همان فایل‌سیستم اتمیک است.
3. در هر شکست، فایل `.partial` حذف می‌شود.
4. رویداد `backup_failed` با دلیل ثبت می‌شود.
5. **هیچ فایل قدیمی‌ای حذف نمی‌شود.**

### شکست Restore

۷ دروازه، به ترتیب. **هر کدام رد شود، مقصد دست‌نخورده می‌ماند:**

| # | دروازه | خطا |
|---|---|---|
| ۱ | magic بایت | «این فایل بکاپ VIRA نیست» |
| ۲ | header JSON | «هدر خراب است» |
| ۳ | رمزگشایی GCM | «کلید اشتباه یا فایل دست‌کاری شده» |
| ۴ | بازکردن gzip | «فایل ناقص یا بریده است» |
| ۵ | `manifest_sha256` | «مانیفست نامعتبر» |
| ۶ | SHA-256 هر عضو | «فایل X خراب است» |
| ۷ | `PRAGMA integrity_check` روی DB استخراج‌شده | «پایگاه داده سالم نیست» |

استخراج در یک پوشهٔ موقت انجام می‌شود، **نه** روی مقصد. فقط پس از عبور هر
۷ دروازه، فایل‌ها جابه‌جا می‌شوند. این الزام مرحلهٔ ۱.۷ است: Restore نباید بدون
تأیید اعتبار، دیتابیس مقصد را تغییر دهد.

**یک استثنا که باید صریح گفته شود.** وقتی Restore رد می‌شود، فرمان یک ردیف
`restore_failed` در `audit_logs` می‌نویسد — و آن جدول در همان پایگاه داده‌ای است
که مقصد Restore است. پس جملهٔ «مقصد دست‌نخورده ماند» به‌طور مطلق درست نیست:

* **هیچ داده‌ای از کانتینر نصب نمی‌شود.** اندازه‌گیری شد: فهرست جدول‌ها و همهٔ
  ردیف‌های غیر `audit_logs`، پیش و پس از یک بازیابی ردشده، یکسان ماندند
  (۵۸ جدول، ۱۵ ردیف، hash یکسان).
* **یک ردیف audit اضافه می‌شود**، پس checksum خود فایل عوض می‌شود.

نخستین متن خروجی فرمان «مقصد تغییر نکرد» بود که با این اندازه‌گیری سازگار نبود و
اصلاح شد. همچنین اگر خود پایگاه داده خراب باشد — که یکی از محتمل‌ترین دلایل
اجرای Restore است — نوشتن همان ردیف audit ممکن است خطا بدهد؛ پس رویداد همیشه
در فایل لاگ هم نوشته می‌شود و خطای ثبت، خطای اصلی را نمی‌پوشاند.

## ۷. ثبت در Audit Log

از همان `AuditRecorder` موجود استفاده می‌شود، نه یک مسیر جدا:

| رویداد | چه زمانی |
|---|---|
| `backup` | بکاپ موفق — با نام فایل، اندازه، تعداد ردیف |
| `backup_failed` | شکست — با دلیل |
| `restore` | بازیابی موفق |
| `restore_failed` | شکست — با دلیل و شمارهٔ دروازه |
| ~~`restore_verified`~~ | **پیاده‌سازی نشد** — توضیح در پایین |

**هیچ‌کدام محتوای بکاپ را ثبت نمی‌کنند.** نام فایل و اندازه بله؛ خود داده نه.

**چرا `restore_verified` رویداد جداگانه نیست.** در طراحی اولیه آمده بود، ولی
`restore` فقط **پس از** `PRAGMA integrity_check` روی پایگاه نصب‌شده نوشته می‌شود؛
اگر آن بررسی رد شود، `restore_failed` ثبت می‌شود. پس دو رویداد برای یک عمل، فقط
یک ردیف تکراری می‌ساخت. به‌جای بزرگ‌کردن سطح لاگ، همین‌جا صریح گفته می‌شود که
`restore` به‌معنی «بازیابی شد و یکپارچگی‌اش تأیید شد» است.

**ترتیب نوشتن، تصادفی نیست.** نخستین نسخهٔ فرمان، جدول زیبای خروجی را **پیش از**
ثبت رویداد چاپ می‌کرد. روی این runtime رندر جدول خطا داد — و نتیجه این شد که
بکاپ نوشته شده بود ولی **هیچ ردیف audit و هیچ pruning اجرا نشد**. رویداد امنیتی
نباید پایین‌دستِ قالب‌بندی باشد؛ اکنون اول ثبت، بعد خروجی.

## ۸. زمان‌بندی

**محدودیت واقعی:** `docs/HOST_COMPATIBILITY.md` هر دو را `BLOCKED` علامت زده —
cron و SSH.

| گزینه | وضعیت |
|---|---|
| cron سمت سرور | **BLOCKED** |
| SSH برای اسکریپت | **BLOCKED** |
| `schedule:run` لاراول | نیاز به cron دارد → BLOCKED |
| **پینگ خارجی به یک route امضاشده** | تنها راه بدون cron |
| fallback پس از پاسخ | ممکن، ولی فقط وقتی کسی وارد شود |

**طراحی:** فرمان `vira:backup` CLI است. روی هاستی که cron دارد، cron صدا می‌زند.
روی هاست فعلی، یک سرویس زمان‌بند بیرونی باید به یک route محافظت‌شده پینگ بزند —
که **در این چرخه پیاده‌سازی نمی‌شود**، چون ساختن یک route که بکاپ را راه بیندازد
بدون تصمیم دربارهٔ امضا و rate-limit، سطح حملهٔ تازه می‌سازد.

## ۹. محدودیت‌های باقی‌مانده

1. **کل payload در حافظه رمزنگاری می‌شود.** با `memory_limit=256M` و سقف
   پیش‌فرض ۶۴ مگابایت، بکاپ بزرگ‌تر **رد می‌شود** نه اینکه حافظه را تمام کند.
   راه‌حل آینده: GCM تکه‌ای با tag به ازای هر تکه.
2. **Off-site واقعی آزموده نشد** — مقصد خارجی در دسترس نبود.
3. **زمان‌بندی خودکار پیاده‌سازی نشد** — cron در دسترس نیست.
4. **بازیابی زیر بار آزموده نشد.**
5. **`storage/app` عملاً خالی است.** بکاپ واقعی «۲ فایل» گزارش کرد، ولی آن دو
   فقط `private/.gitignore` و `public/.gitignore` هستند — هیچ پیوست واقعی در
   سامانه نیست. پس مسیر فایل‌ها در کانتینر **اجرا شده** (ساخته، رمزنگاری،
   استخراج، بازگردانی، و مقایسهٔ بایت‌به‌بایت در `BackupRestoreTest`) ولی با دادهٔ
   واقعی مشتری آزموده نشده. `.gitignore`ها عمداً نگه داشته می‌شوند: بازیابی بدون
   آن‌ها قواعد ignore را عوض می‌کند.
6. **این محیط php-wasm است، نه هاست مقصد.** `env-capabilities.php` باید روی هاست
   واقعی اجرا شود؛ GCM به OpenSSL ≥ 1.0.1 و PHP ≥ 7.1 نیاز دارد.

## ۱۰. آنچه اجرای واقعی نشان داد

این بخش بعد از **اجرا** نوشته شده، نه از روی طراحی. هر مورد با اندازه‌گیری ثبت شده
است؛ مواردی که تنها روی کاغذ درست بودند همان‌جا اصلاح شدند.

### ۱۰.۱ دو خطای واقعی که اجرا کشف کرد

| # | خطا | چگونه پیدا شد | نتیجه |
|---|---|---|---|
| ۱ | مانیفست دو بار encode می‌شد — یک بار با `JSON_PRETTY_PRINT` برای عضو آرشیو، یک بار بدون آن برای hash. دو رشتهٔ بایت متفاوت، پس **هر کانتینری در دروازهٔ ۵ رد می‌شد** و هیچ بکاپی قابل بازیابی نبود | `BackupRestoreTest::testRoundTripRestoresEveryRow` — نخستین اجرای سوئیت | یک بار encode، همان رشته هم در آرشیو هم در hash |
| ۲ | منطق pruning همهٔ فایل‌های N دورهٔ آخر را نگه می‌داشت، دسته‌ها روی هم می‌افتادند و **هیچ‌چیز حذف نمی‌شد** (`pruned : 0` با ۲۱ کانتینر) | اجرای واقعی فرمان با ۲۰ کانتینر با mtime پخش‌شده | منطق به `RetentionPolicy` منتقل و با ۴ آزمون قفل شد؛ اکنون `pruned : 12` |

هیچ‌کدام با «کد درست به‌نظر می‌رسد» پیدا نمی‌شدند. مورد ۱ فقط با یک بازیابی واقعی
و مورد ۲ فقط با پرونده‌های چند روز مختلف آشکار می‌شود.

### ۱۰.۲ محدودیت‌های همین runtime (php-wasm)

* **`artisan list` crash می‌کند** — polyfill مربوط به `ext-intl` با کلاس موجود
  برخورد می‌کند و رندر جدول کنسول `Normalizer` را پیدا نمی‌کند. این اشکال
  php-wasm است نه فرمان‌ها: `artisan vira:backup`، `vira:restore` و
  `vira:backup-key` هر سه exit=0 می‌دهند.
* به همان دلیل، **`$this->table()` در فرمان‌ها استفاده نمی‌شود** و خروجی با
  `line()` نوشته می‌شود. این فقط زیبایی نیست: همان crash باعث شد ثبت audit
  اجرا نشود (بند ۷).
* **stdin بسته است**، پس `confirm()` مقدار پیش‌فرض (`no`) را می‌گیرد. برای اجرای
  غیرتعاملی باید `--no-interaction` داده شود؛ `--force` به‌تنهایی کافی نیست چون
  تأیید تعاملی هنوز پرسیده می‌شود.

### ۱۰.۳ آنچه روی هاست واقعی باید دوباره اجرا شود

`tools/checks/env-capabilities.php` همان فهرست توانمندی‌ها را روی هاست مقصد چاپ
می‌کند. تا وقتی اجرا نشده، هیچ‌کدام از فرض‌های بخش ۰ برای آن هاست تأیید نیست.

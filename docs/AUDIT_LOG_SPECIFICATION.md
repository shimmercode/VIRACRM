# مشخصات گزارش رویدادها (Audit Log)

این سند رفتار واقعی `audit_logs` را توصیف می‌کند: چه چیزی نوشته می‌شود، چه چیزی
پوشانده می‌شود، و — مهم‌تر از هر دو — چه چیزی **نوشته نمی‌شود**.

## چرا یک نقطهٔ ورود

هر رویداد قابل گزارش از `App\Services\Security\AuditRecorder` عبور می‌کند. دلیلش در
کامنت همان کلاس آمده: تا پوشاندن (redaction) در یک کنترلر فراموش‌شدنی نباشد. اگر
هر کنترلر خودش `AuditLog::create()` می‌کرد، یک مسیرِ تازه می‌توانست رمز عبور را
وارد `changes` بنویسد و هیچ‌کس متوجه نمی‌شد.

## جدول

`audit_logs` — در پایگاه نمونه ۲۳۲ ردیف.

| ستون | معنا |
|---|---|
| `id` | شناسه |
| `user_id` | کاربر انجام‌دهنده؛ برای `login_failed` می‌تواند `NULL` باشد |
| `event` | نام رویداد (فهرست زیر) |
| `subject_type` | کلاس کامل مدل، مثل `App\Models\Contract` |
| `subject_id` | شناسهٔ رکورد |
| `description` | توضیح فارسی |
| `changes` | JSON مجموعهٔ تغییرات، **پوشانده‌شده** |
| `ip` | نشانی IP |
| `user_agent` | عامل کاربری |
| `created_at` | زمان |

ایندکس‌ها روی `(subject_type, subject_id)`، `created_at` و `event` هستند — یعنی سه
پرسش رایج «تاریخچهٔ این رکورد»، «رویدادهای این بازه» و «همهٔ رویدادهای این نوع»
اینکس دارند.

## رویدادها

ثابت‌های `AuditRecorder` و تعداد واقعی هر کدام در پایگاه نمونه:

| ثابت | `event` | نمونه | معنا |
|---|---|---|---|
| `CREATED` | `created` | 10 | ایجاد رکورد |
| `UPDATED` | `updated` | 9 | ویرایش رکورد، با `changes` |
| `DELETED` | `deleted` | 0 | حذف نرم |
| `REVEALED` | `revealed` | 0 | **نمایش** یک راز ذخیره‌شده |
| `EXPORTED` | `exported` | 0 | **بیرون‌بردن** داده (PDF/خروجی) |
| `LOGIN` | `login` | 168 | ورود موفق |
| `LOGIN_FAILED` | `login_failed` | 11 | ورود ناموفق، با دلیل |
| `LOGOUT` | `logout` | 7 | خروج |
| `DENIED` | `denied` | 27 | تلاش برای مسیر بدون مجوز |

دو رویداد `REVEALED` و `EXPORTED` مهم‌ترین‌های این جدول‌اند: خواندن یک رمز عبور از
پشت رمزنگاری، و خارج کردن مجموعه‌ای از رازها در یک فایل، هر دو از جنس «داده از
مرز سیستم بیرون رفت» هستند و باید رد پای جدا از «ویرایش رکورد» داشته باشند.

`denied` عمداً ثبت می‌شود: `EnsurePermission` قبل از `abort(403)` آن را می‌نویسد،
پس ۲۷ رکورد موجود یعنی این مسیر واقعاً اجرا شده است.

## پوشاندن (Redaction)

`AuditLog::redact()` روی `changes` اجرا می‌شود، در `AuditRecorder::record()` — یعنی
**بعد از** اینکه کنترلر تغییرات را ساخت و **قبل از** نوشتن. هر کلیدی که یکی از این
تکه‌ها را در نامش داشته باشد (بی‌توجه به بزرگی و کوچکی حروف) جای مقدارش
`[redacted]` می‌شود:

```
password, passwd, secret, token, api_key, apikey,
ciphertext, private_key, encryption_key, remember_token,
credential, authorization, cookie
```

چند نکته که عمداً این‌طور است:

1. **تطبیق زیررشته است، نه تساوی.** پس `user_password_hash` هم گرفته می‌شود، نه
   فقط `password`. این تصمیم هزینه دارد: یک ستون بی‌خطر مثل `token_count` هم
   پوشانده می‌شود. در برابر نشت راز، این هزینه پذیرفته شده است.
2. **آرایه‌های تودرتو هم باز می‌شوند** و بازگشتی بررسی می‌شوند.
3. **`NULL` دست‌نخورده برمی‌گردد** — نبودِ تغییرات با تغییراتِ پوشانده‌شده فرق دارد.

## آنچه این سیستم ثبت نمی‌کند

صادقانه، چون گزارش رویدادی که ادعای کامل بودن کند بدتر از نبودِ آن است:

1. **هیچ رابط کاربری برای خواندن این جدول وجود ندارد.** هیچ مسیری با `audit` در
   جدول مسیرها نیست، هیچ فایل Blade مرتبطی وجود ندارد، و رشتهٔ `audit.view` در
   کل `app/` و `routes/` پیدا نمی‌شود — با اینکه این مجوز در جدول `permissions`
   هست. یعنی داده جمع می‌شود ولی تنها راه خواندنش کوئری مستقیم به پایگاه داده
   است. این یک شکاف باز است، نه یک تصمیم.
2. **هیچ سازوکار نگهداری/پاک‌سازی نیست.** هیچ دستور کنسولی برای بایگانی یا حذف
   رویدادهای قدیمی وجود ندارد؛ جدول بی‌نهایت رشد می‌کند.
3. **خواندنِ فهرست‌ها ثبت نمی‌شود.** فقط `revealed` و `exported` ثبت می‌شوند، نه
   «کاربر صفحهٔ اعتبارنامه‌ها را باز کرد».
4. **تغییراتِ سطح فیلد برای همهٔ مدل‌ها ثبت نمی‌شود.** `updated` تنها جایی نوشته
   می‌شود که کنترلر صریحاً `AuditRecorder::updated()` را صدا بزند.

**تاریخ:** ۲ آذر ۱۴۰۵ · **مبنای تصمیم کارفرما:** Internal Accounting (قطعی، تکرارنشود)

## ۱. اصول غیرقابل مذاکره (۶ اصل)

### اصل ۱ — ثبت دوطرفه (Double-Entry)

هر سند: **جمع بدهکار = جمع بستانکار**، همیشه، در سطح سند و در سطح خط.

```
CHECK (SUM(debit) = SUM(credit)) enforced at posting, not at insert.
```
سند ناتراز **قابل ثبت (post)** نیست. این یک قاعدهٔ دیتابیسی است، نه توصیهٔ UI.

### اصل ۲ — درآمد ≠ دریافت وجه

| رویداد | ثبت |
|--------|-----|
| شناسایی درآمد | بدهکار: حساب دریافتنی · بستانکار: درآمد |
| وصول وجه | بدهکار: بانک · بستانکار: حساب دریافتنی |

**دو سند جدا. هرگز ادغام نمی‌شوند.**

### اصل ۳ — هزینه ≠ پرداخت

| رویداد | ثبت |
|--------|-----|
| شناسایی هزینه | بدهکار: هزینه · بستانکار: حساب بدهی |
| پرداخت | بدهکار: حساب بدهی · بستانکار: بانک |

### اصل ۴ — انتقال داخلی

انتقال بانک → صندوق: **نه درآمد، نه هزینه.**

```
بدهکار: صندوق   ۱۰٬۰۰۰٬۰۰۰
بستانکار: بانک  ۱۰٬۰۰۰٬۰۰۰
```

هیچ حساب درآمد/هزینه‌ای لمس نمی‌شود. اگر سند انتقال به حساب درآمد بخورد،
**صورت سود و زیان جعلی می‌شود** — این خطای رایج سیستم‌های ساده است.

### اصل ۵ — اسناد قطعی تغییرناپذیر

سند `posted` **مستقیماً ویرایش یا حذف نمی‌شود**. اصلاح فقط از طریق:
- **سند برگشتی (Reversal)**: سند معکوس که به سند اصلی ارجاع می‌دهد
- **سند اصلاحی (Adjustment)**: تفاوت را ثبت می‌کند

هر دو در Audit ثبت می‌شوند و سند اصلی دست‌نخورده می‌ماند.

### اصل ۶ — دقت مالی

| قاعده | پیاده‌سازی |
|-------|-----------|
| بدون Floating Point | `BIGINT` به **ریال** — همان تصمیم موجود پروژه (`integer`) |
| واحد پول شفاف | DB: ریال · UI: تومان با برچسب صریح · تبدیل فقط در نمایش |
| تبدیل پنهان ممنوع | هر عددی که تومان است، برچسب «تومان» دارد |
| گرد کردن قاعده‌مند | فقط در تقسیم‌های پورسانت/مالیات؛ `ROUND_HALF_UP` در سطح ریال |
| قابل بازتولید | هر سند ورودی‌هایش را snapshot می‌کند |

**نکتهٔ ریسک:** `BIGINT` ریال تا ~۹۲۲ هزار میلیارد تومان ظرفیت دارد — کافی است.

`journal_entries.source_type` + `source_id` به یکی از این‌ها اشاره می‌کند:
`Customer` · `Contract` · `Project` · `PayrollPeriod` · `null` (سند دستی)

**این همان الگوی `scheduled_events` است** که در پروژه وجود دارد — سازگار.

## ۴. ساختار اسناد

### `journal_entries`

| ستون | نوع | قاعده |
|------|-----|-------|
| `id` | bigint | — |
| `number` | string(32) | `VIRA-JE-000123` — یکتا، فقط در post صادر می‌شود |
| `fiscal_year_id` | FK | — |
| `date` | date | تاریخ سند (میلادی ذخیره، شمسی نمایش) |
| `status` | enum | `draft` \| `posted` \| `reversed` |
| `total_debit` / `total_credit` | bigint | برابر در post |
| `source_type` / `source_id` | string/bigint | nullable |
| `reversal_of_id` | FK self | برای سند برگشتی |
| `created_by` / `posted_by` / `posted_at` | — | Audit |

### `journal_entry_lines`

| ستون | نوع | قاعده |
|------|-----|-------|
| `entry_id` | FK cascade | — |
| `account_id` | FK restrict | باید `is_postable` باشد |
| `debit` / `credit` | bigint | **exactly one > 0**, other = 0 |
| `party_id` | FK nullable | طرف حساب |
| `description` | string | — |

**Constraints:**
```sql
CHECK (debit >= 0 AND credit >= 0)
CHECK ((debit > 0) <> (credit > 0))     -- دقیقاً یکی
UNIQUE (entry_id, line_no)
```

## ۵. چرخه عمر سند

```
   ┌─────────┐  post (تأیید توازن)  ┌────────┐
   │  draft  │ ───────────────────► │ posted │
   └────┬────┘                      └───┬────┘
        │ حذف مجاز                      │ reverse
        ▼                               ▼
     (پاک)                        ┌──────────┐
                                  │ reversed │  ← سند اصلی تغییر نمی‌کند
                                  └──────────┘
```

| گذار | شرط |
|------|-----|
| draft → posted | توازن ✓ · تاریخ در دورهٔ باز ✓ · حساب‌ها postable ✓ · مجوز `accounting.post` |
| posted → reversed | مجوز `accounting.reverse` · دلیل الزامی · سند معکوس خودکار |
| posted → draft | **ممکن نیست** — باید برگشت بخورد |

**شمارهٔ سند** فقط در `post` صادر می‌شود، پیوسته و بدون شکاف در هر دورهٔ مالی.

**دورهٔ بسته:** `fiscal_years.is_closed = true` → هر ثبت با تاریخ آن دوره رد می‌شود.

## ۶. سناریوهای عددی واقعی (الزام دستور §8.7)

> مبالغ نمونه برای توضیح منطق. همه به **تومان**، ذخیره به ریال (×۱۰).

### سناریو ۱ — قرارداد ۱۰۰ میلیون تومانی، وصول ۳۰ میلیون

**رویداد A: شناسایی درآمد**
```
تاریخ ۱۴۰۵/۰۹/۰۱ · سند VIRA-JE-000001 · منبع: Contract#12
─────────────────────────────────────────────────────
۱۲۰۰ حساب دریافتنی (مشتری الف)   بدهکار ۱۰۰٬۰۰۰٬۰۰۰
۴۱۰۰ درآمد پروژه‌های سئو                    بستانکار ۱۰۰٬۰۰۰٬۰۰۰
                                          ─────────────
                              جمع:        ۱۰۰٬۰۰۰٬۰۰۰ = ۱۰۰٬۰۰۰٬۰۰۰ ✓
```
**حساب‌های لمس‌شده:** دارایی ↑ · درآمد ↑. **بانک لمس نشد** — چون پولی نرسیده.

**رویداد B: وصول ۳۰ میلیون** (۱۴۰۵/۰۹/۱۰)
```
سند VIRA-JE-000002 · منبع: Contract#12
─────────────────────────────────────────────────────
۱۲۱۰ بانک — حساب اصلی          بدهکار ۳۰٬۰۰۰٬۰۰۰
۱۲۰۰ حساب دریافتنی (مشتری الف)             بستانکار ۳۰٬۰۰۰٬۰۰۰
```
**نتیجه:** دریافتنی = ۷۰٬۰۰۰٬۰۰۰ باقی می‌ماند. **درآمد دوباره ثبت نشد** (اصل ۲).

### سناریو ۲ — وصول ۲۰ میلیون دیگر (۱۴۰۵/۱۰/۰۵)

```
سند VIRA-JE-000003
─────────────────────────────────────────────────────
۱۲۱۰ بانک                     بدهکار ۲۰٬۰۰۰٬۰۰۰
۱۲۰۰ حساب دریافتنی                        بستانکار ۲۰٬۰۰۰٬۰۰۰
```
**مانده دریافتنی: ۵۰٬۰۰۰٬۰۰۰** — قابل مشاهده در «مطالبات».

### سناریو ۳ — هزینهٔ ۱۵ میلیون با پرداخت بعدی

**رویداد A: شناسایی هزینه (۱۴۰۵/۰۹/۱۵)**
```
سند VIRA-JE-000004
─────────────────────────────────────────────────────
۵۳۰۰ هزینه‌های فنی/ابزار       بدهکار ۱۵٬۰۰۰٬۰۰۰
۲۱۰۰ حساب پرداختنی (تأمین‌کننده)           بستانکار ۱۵٬۰۰۰٬۰۰۰
```
**رویداد B: پرداخت (۱۴۰۵/۰۹/۲۵)**
```
سند VIRA-JE-000005
─────────────────────────────────────────────────────
۲۱۰۰ حساب پرداختنی            بدهکار ۱۵٬۰۰۰٬۰۰۰
۱۲۱۰ بانک                                  بستانکار ۱۵٬۰۰۰٬۰۰۰
```
**نتیجه:** بدهی صفر. **هزینه یک بار ثبت شد** — نه دو بار (اصل ۳).

### سناریو ۴ — انتقال ۱۰ میلیون بانک به صندوق

```
سند VIRA-JE-000006
─────────────────────────────────────────────────────
۱۱۰۰ صندوق                    بدهکار ۱۰٬۰۰۰٬۰۰۰
۱۲۱۰ بانک                                  بستانکار ۱۰٬۰۰۰٬۰۰۰
```
**بدون اثر بر سود و زیان.** اگر کسی این را به‌عنوان درآمد ثبت کند، صورت مالی
**جعلی** می‌شود. این تست باید در پذیرش باشد.

### سناریو ۵ — برگشت یک سند قطعی

فرض: سند ۵ (پرداخت ۱۵ میلیون) اشتباه بود.

```
سند اصلی VIRA-JE-000005 → status = reversed
سند برگشتی VIRA-JE-000007 (reversal_of_id = 5)
─────────────────────────────────────────────────────
۱۲۱۰ بانک                     بدهکار ۱۵٬۰۰۰٬۰۰۰
۲۱۰۰ حساب پرداختنی                        بستانکار ۱۵٬۰۰۰٬۰۰۰
```
**سند ۵ دست‌نخورده ماند.** اثر خالص صفر. هر دو در دفتر کل دیده می‌شوند.

## ۷. حقوق و دستمزد داخلی

**تصمیم قطعی کارفرما:** حقوق ثابت + اقلام دستی. **بدون فرمول پورسانت خودساخته.**

```
پرداخت حقوق (رویداد ۱ — شناسایی)
─────────────────────────────────────────────────────
۵۱۰۰ حقوق و دستمزد            بدهکار X
۲۲۰۰ حقوق پرداختنی                        بستانکار X

پرداخت حقوق (رویداد ۲ — تسویه)
─────────────────────────────────────────────────────
۲۲۰۰ حقوق پرداختنی            بدهکار X
۱۲۱۰ بانک                                  بستانکار X
```

**نکتهٔ مهم:** `payslips` (موجود در Schema) و `journal_entries` **دو چیز جدا** هستند:
- `payslips` = محاسبهٔ حقوق فردی (مدیریت منابع انسانی)
- `journal_entries` = اثر مالی کل دوره (حسابداری)

پل بین آن‌ها: یک سند تجمیعی به‌ازای هر دورهٔ حقوق، با `source_type = PayrollPeriod`.

## ۸. گزارش‌های مالی

| گزارش | مبنا | Query |
|-------|------|-------|
| دفتر روزنامه | همهٔ اسناد posted | ترتیب تاریخ + شماره |
| دفتر کل | یک حساب | Σ debit − Σ credit |
| تراز آزمایشی | همهٔ حساب‌ها | باید **صفر** شود |
| سود و زیان | حساب‌های income/expense | Σ درآمد − Σ هزینه |
| جریان نقدی | حساب‌های نقدی | تغییر مانده |
| مالی پروژه | `source_type=Project` | سود هر پروژه |
| مالی مشتری | `source_type=Customer` | مانده + گردش |

**قاعدهٔ سخت:** تراز آزمایشی اگر صفر نشود، **باگ است** — نه «اختلاف جزئی».

## ۱۲. تصمیم‌های باز حسابداری (نیازمند کارفرما)

| ID | سؤال | پیشنهاد |
|----|------|---------|
| **OD-41** | کدینگ حساب‌ها بالا مناسب است؟ | بله، ۴ سطحی |
| **OD-42** | دورهٔ مالی: شمسی (فروردین–اسفند) یا میلادی؟ | **شمسی** |
| **OD-43** | آیا نیاز به چند صندوق/چند حساب بانکی هم‌زمان؟ | بله |
| **OD-44** | مالیات بر درآمد/حقوق در Scope هست؟ | **خیر** (خارج از Scope اعلامی) |
| **OD-45** | آیا گردش حساب مشتری (Statement) برای مشتری قابل ارسال است؟ | پیشنهاد: بله، PDF |
| **OD-46** | روش هزینه‌یابی پروژه (مستقیم یا سربار توزیعی)؟ | مستقیم |
| **OD-47** | بستن دوره: خودکار یا دستی؟ | دستی با تأیید مدیر |

**هیچ‌کدام را خودم پیاده نمی‌کنم.**
